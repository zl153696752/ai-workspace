# 企业级 Agent 项目改造方案

> 本文档只记录改造的目标、范围、模块设计与实施步骤等关键信息，作为施工蓝图。
>
> 不记录具体代码改动方式、不记录零碎小问题。代码层面的实现细节另行讨论。

## 一、目标与原则

- **目标**：把当前偏 demo 的单 Agent RAG，升级为「小而美、五脏俱全」的企业级 Agent 项目，最终仍发布到 ModelScope 单容器。
- **原则**：
  - 功能齐全但不堆砌，每加一项都要能讲清「为什么值得」。
  - 依赖尽量不膨胀，优先复用已有能力与标准库。
  - 一切设计以 ModelScope 约束为前提：单容器、CPU 推理、无外部服务、出网受限。
  - 生产路径只保留一种编排实现（多 Agent 图），旧的对照实现在改造中清理。
  - **韧性兜底（分层降级、失败留痕、永不裸奔）**：每个可能失败的环节都要有明确降级路径，失败时给用户体面回应而非崩溃/空白，同时记一笔日志/trace 便于排查。只做必要兜底、不做过度兜底——重试只在模型调用收口层做（不层层重试），降级不得静默吞异常；「模型答错」靠事前预防与离线评估解决，不做在线自动纠错（详见决策 6）。

## 二、范围边界

**做：**

- RAG 质量三件套（结构化切片 + 混合检索 + Reranker）与 Self-CRAG 质检
- 多 Agent 编排（真实职责拆分，唯一生产路径）
- 后端 JWT 真鉴权 + 游客/亮哥双身份 + 私人内容隔离
- SQLite 会话持久化 + tenacity 韧性
- 可观测性第一档（token/成本/延迟）+ 第二档（自建轻量 trace）
- Agent 长期记忆（跨会话，轻量方案 + 治理）
- 代码清理（删对照实现）+ 依赖精简
- 离线 RAG 评估脚本
- Prompt 注入防御（输入与检索内容护栏，**必做**）

**不做：**

- 第三档可观测性（LangSmith / OpenTelemetry / Langfuse 等外部平台）
- 多租户（只保留游客、亮哥两个身份）
- ORM、Postgres、Redis 等重型工程化组件
- 把 RAG 评估做成常驻服务
- 记忆系统的「每轮抽取」与「框架 Store」重型方案

## 三、已确认的关键决策

1. **Reranker 模型**：`bge-reranker-base` 的 ONNX int8（容器内存宽裕时可升级 `bge-reranker-v2-m3`）。模型文件需手动放入模型资产目录；代码在模型缺失时优雅降级为纯 RRF 排序，不影响系统运行。
2. **新增依赖**：仅 `jieba`（中文分词）与 `rank_bm25`（关键词打分）。其余能力（JWT、重试、ONNX 推理、编排）均已在现有依赖中。
3. **数据持久化**：SQLite，使用 Python 标准库 `sqlite3`，不引入 ORM。
4. **编排实现**：删除手写版与 LangChain 版对照代码，多 Agent 图为唯一生产路径。
   - 注意：删的是「对照代码」，不是 langchain 相关「库」；多 Agent 图仍依赖 LangChain 生态（模型客户端、工具封装、MCP 适配）。
   - 共享零件（知识库工具封装、技能加载、模型客户端）保留复用。
5. **知识库测试/演示语料方向**：采用虚构「牛来数码」公司设定（对内答公司制度、对外答产品）。知识库含公司制度 + 产品目录（型号/参数/价格/保修）+ 售后 FAQ，刻意埋入“相似但不同”的区分度陷阱（如 N7 / N7 Pro / N7s 参数各异），用于验证混合检索与精排的价值。语料须原创虚构（不用真实淘宝内容，规避版权与营销噪音）、事实密集、可标注金标准。牛来的人格/规矩等写死提示词可随时修改，语料主题不受其现有定位约束。
6. **「模型答错」的处理**：不做在线自动纠错（再叫一个模型核查会同样出错、且徒增延迟与成本）；改为事前预防——强制 grounding（照资料答 + 编号引用）、人格允许「没把握就说不知道、禁止编造」、护栏（越界/有害/泄露内部信息一律拒答；**防 prompt 注入**——用户输入或检索内容里试图改写指令、套取系统提示词、诱导越权时一律不执行，只按既定人格与规则作答）、需结构化输出时解析失败则重试或降级。答案对错交给步骤 10 离线评估量化，据此改 prompt / 检索 / 语料，而非在线兜底。

## 四、模块设计（能力层面，不含实现细节）

### 模块 1 · RAG 质量层

- **结构化切片**：替代当前「压平换行 + 定长硬切」，改为按标题/段落分节，切片携带结构元数据。
- **混合检索**：向量召回 + 关键词（分词 + BM25）召回，用 RRF（倒数排名融合）合并，不引入加权调参。
- **Reranker 精排**：召回阶段宽松取较多候选，精排阶段收窄到少量高质量结果，彻底替代旧的距离硬阈值。
- **Self-CRAG 质检**：精排后判定资料相关性；不相关则如实告知「无资料」，或有界地重写查询重检一次。
- **检索兜底**：召回为空或资料不相关由 Self-CRAG 处理（如实告知 / 有界重写重查一次）；Reranker 模型缺失降级为纯 RRF；检索层任何异常（向量库/BM25 索引报错、超时）都须 catch 并降级为「无上下文谨慎回答或致歉」，绝不把堆栈抛给用户。

### 模块 2 · 多 Agent 编排（唯一生产路径）

- 基于 LangGraph 手写 StateGraph，共享状态贯穿各节点。
- **Supervisor**：意图识别与路由。
- **检索质检 worker**：改写 → 混合召回 → 精排 → 质检（承接模块 1 能力）。
- **工具 worker**：集中管理 MCP 外部工具（网页抓取、天气），主 Agent 不再平铺全部工具。
- **合成 worker**：基于质检过的资料生成回答，流式输出 + 编号引用；施加 prompt 注入护栏（把资料当数据不当指令、拒绝改写人格/套取系统提示词/诱导越权）。
- 拆分原则：每个 worker 有独立职责，避免「为多 Agent 而多 Agent」。
- **编排韧性（防「互相甩锅」）**：设 `recursion_limit` 步数上限并捕获 `GraphRecursionError`，超限走兜底合成或致歉，杜绝死循环/踢皮球；Supervisor 设默认路由（catch-all），某 worker 失败或返回空则跳过它、带已有信息继续；每个状态单一 owner，无 worker 认领时回落默认路径。

### 模块 3 · 鉴权与私人内容隔离

- **双身份**：游客（无 token，仅公共内容）、亮哥（登录持 token，解锁私人内容）。
- **鉴权**：口令与密钥仅存后端环境变量，绝不进前端包；登录签发长效 token（默认 30 天），前端保存 token 并在请求头携带。
- **私人隔离**：上传时可标记文档为「私人」；检索时游客自动过滤私人内容；私人文档的下载/删除仅限亮哥。

### 模块 4 · 会话持久化 + 韧性 + 可观测性

- **会话持久化**：后端 SQLite 存会话，重启/换端历史不丢；前端改为「后端优先 + 本地缓存兜底」。
- **韧性**：所有模型调用统一收口，包重试、超时、降级。
- **可观测性第一档**：记录每次模型调用的 token、成本、延迟。
- **可观测性第二档**：把一次问答的全链路（改写→召回→精排→质检→合成，各步耗时与 token）记为一条结构化 trace 存 SQLite；可选极简查看入口。
- 说明：韧性与两档可观测性都在模型调用收口处一并实现，避免逻辑散落；各层兜底/降级触发都要记进 trace（降级留痕），不允许静默吞异常。

### 模块 5 · RAG 评估（离线，不进运行时）

- **评估集生成**：由 LLM 读取知识库文档，自动生成问答对（问题 + 参考答案 + 参考来源）。
- **评估执行**：检索层出 Recall@k / MRR / NDCG；生成层用 LLM-as-judge 打忠实度、答案相关性；产出报告。
- 定位：开发期离线工具，不打包进 ModelScope 运行时。

### 模块 6 · Agent 长期记忆（跨会话）

- **定位**：亮哥专属；游客不记不读。区别于短期记忆（会话历史，已由模块 4 覆盖）。
- **判断该记什么**：由 LLM「记忆官」按评判清单抽取——记身份/画像、稳定偏好、长期事实、明确指令、重要决定及理由；不记一次性任务细节、闲聊、本轮中间过程、瞬时状态。总闸：「跨会话是否仍有价值且稳定」。
- **隐私红线**：密码、令牌、身份证、银行卡等敏感信息，即使被要求也绝不记录。
- **时机（轻量方案）**：会话结束时异步抽取，主链路零延迟；抽取看完整段对话，判断更干净。
- **触发策略**：新开对话时惰性补抽上一段 / 每积累 N 轮增量抽取 / 闲置补做 / 强信号（「记住…」「我喜欢…」「以后都…」）即时捕获。
- **去重与冲突**：入库前与已有记忆比对，决定新增/更新/删除旧的/跳过，防止记忆自相矛盾。
- **存储与注入**：记忆条目带类别与关键词存储；提问时复用混合检索捞出相关记忆，注入合成提示词。
- **治理入口**：提供「我的记忆」查看/删除，作为记错时的纠错托底。
- **原则**：宁可不记，不要记错。

### 模块 7 · 代码与依赖清理

- **代码清理**（在多 Agent 图成为生产路径后进行）：删除手写版与 LangChain 版对照代码、旧的单 Agent 图、相关旧开关；保留共享零件与 langchain 库。
- **依赖精简**（压轴进行）：以「重建干净虚拟环境 + 只声明直接依赖 + 冻结生成精确依赖清单」的方式收敛 `requirements.txt`，避免肉眼删行误删间接依赖。
- **死文件清理**：候选文件逐个确认后再删，不擅自清理。

### 模块 8 · 部署适配（ModelScope）

- 构建镜像安装新依赖、打包 Reranker 模型资产；核验 ONNX 未变成 LFS 指针文件。
- **知识库语料与 seed 机制**：保留 `seed.py`「每次冷启动灌库」机制——因 `uploads/`、`chroma_db/` 被 gitignore 且创空间容器临时，手动上传会在重启后丢失，故线上公共底料必须靠 seed 预置，**绝不删 seed**；将种子文档由硬编码字符串改为读取随仓库提交的 `backend/seed_docs/*.txt`（内容见决策 5 的「牛来数码」语料），Dockerfile 增加对应 COPY。`upload` 接口保留，定位为运行时临时加料与私人文档（模块 3），不作为线上底料来源。私人示例文档不预置。
- CPU 上多 Agent 会放大延迟，worker 数量与重试次数需克制。

## 六、编码约定

- 模块划分合理、单一职责：既不把一大堆逻辑全挤在一起，也不把逻辑拆得过散。
- 保持与现有代码库一致的详细教学式注释风格。
- 具体代码如何改，逐个模块另行讨论后再动手，不在本文档展开。

## 七、关键风险与约束

- **模型资产**：ONNX 走 LFS 时若未正确推送，会变成极小的指针文件打进镜像，需在提交后核验文件大小。
- **切片变更**：结构化切片会改变切片边界，需重新灌库。
- **依赖精简**：`requirements.txt` 中多数为间接依赖，禁止肉眼删行，必须用重建冻结法。
- **记忆触发**：Web 场景无天然「会话结束」信号，需靠惰性/轮次/闲置/强信号策略替代。
- **CPU 延迟**：精排与多 Agent 叠加会放大延迟，需控制召回量与 worker 数量。

## 八、待议项（本次改造完成后再讨论，暂不实施）

**工程增强（二档，先记录）：**

- 并发与性能：CPU 单容器的并发承载与单次问答延迟，需实测数据；当前检索为同步嵌入，注意阻塞。
- 代码测试策略：单元测试 / 集成测试（现仅有 RAG 离线评估，缺代码层测试）。
- 语义缓存：高频问题缓存结果，降延迟与成本（CPU 部署下的可选优化）。
- 限流与成本预算：防刷爆、控制 token 成本。

**面试待答的选型理由（三档，改造完再备话术）：**

- 为什么 SQLite 不用 Postgres、不上 ORM？
- 为什么 RRF 不用加权融合？
- 为什么 ONNX + int8 不用 torch？
- 为什么 Chroma 不用 Milvus / FAISS？
- 为什么 cross-encoder 放召回后、不直接全库精排？
