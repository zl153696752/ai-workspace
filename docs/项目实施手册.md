## 四、第一步：环境准备（手把手版）

### 4.1 检查/安装基础软件

**打开 PowerShell**（Win 键 → 输入 powershell → 回车），依次输入以下命令检查：

**① 检查 Python**

### 4.4 初始化后端（在 PyCharm 的 Terminal 里执行）

**① 创建虚拟环境（重点理解这个）**

```powershell
python -m venv venv
```

> 💡 这句是什么意思？
>
> **虚拟环境** = 给这个项目单独建一个“包仓库”。这样这个项目装的包不会和别的项目冲突（类似前端每个项目有自己的 node_modules，而不是全局装）。
>
> 执行后 backend 目录下会多出一个 `venv` 文件夹，里面是这个项目专用的 Python 和包。
>
> 命令执行完没有任何输出是正常的，等 10-30 秒。

**② 激活虚拟环境**

```powershell
.\venv\Scripts\Activate.ps1
```

- 注意开头是 `点+反斜杠`：`.\`，PowerShell 里执行当前目录脚本必须这么写。
- 激活成功的标志：命令行开头出现 `(venv)` 前缀，例如：
  ```
  (venv) PS D:\ai-workspace\backend>
  ```
- **如果报错“禁止运行脚本/execution policy”**（Windows 安全策略拦截，很常见），先执行这一句再重试：
  ```powershell
  Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
  ```
  中间弹出询问输入 `Y` 回车。这个只需执行一次，以后永久生效。
- 以后每次新开终端写后端代码前，都要先执行这句激活。不想干了就执行 `deactivate` 退出。

**③ 安装后端依赖**

```powershell
pip install fastapi uvicorn openai python-dotenv
```

> 💡 每个包是干什么的：
>
> - `fastapi`：Web 框架，写接口用的（类似前端的 Express）
> - `uvicorn`：服务器，负责把 FastAPI 跑起来（类似 node xxx.js 启动服务）
> - `openai`：调用大模型 API 的 SDK（DeepSeek 兼容 OpenAI 格式，所以用它）
> - `python-dotenv`：读 .env 配置文件用的（存 API Key）
>
> `pip` 是 Python 的包管理器 = 前端的 npm/pnpm。
>
> 如果下载慢，换清华镜像：
>
> ```powershell
> pip install fastapi uvicorn openai python-dotenv -i https://pypi.tuna.tsinghua.edu.cn/simple

## 五、第二步：最小功能（流式对话）

### 5.1 后端 `backend/app/main.py`

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import StreamingResponse
from openai import OpenAI
import os
from dotenv import load_dotenv

load_dotenv()

app = FastAPI(title="AI Workspace")

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_methods=["*"],
    allow_headers=["*"],
)

client = OpenAI(
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com"
)

@app.post("/api/chat")
async def chat(message: str):
    """流式对话接口"""
    def generate():
        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=[{"role": "user", "content": message}],
            stream=True
        )
        for chunk in response:
            if chunk.choices[0].delta.content:
                yield chunk.choices[0].delta.content

    return StreamingResponse(generate(), media_type="text/plain")
```

### 5.4 前端 `frontend/src/app/page.tsx`

用 VSCode 打开 frontend 项目，在左侧找到 `src/app/page.tsx`，把里面的内容**全部删掉**，换成下面的代码：

```tsx
"use client";
import { useState } from "react";

export default function Home() {
  const [input, setInput] = useState("");
  const [messages, setMessages] = useState<{role: string, content: string}[]>([]);
  const [loading, setLoading] = useState(false);

  const sendMessage = async () => {
    if (!input.trim()) return;

    const userMsg = { role: "user", content: input };
    setMessages(prev => [...prev, userMsg]);
    setInput("");
    setLoading(true);

    const response = await fetch(
      "http://localhost:8000/api/chat?message=" + encodeURIComponent(input),
      { method: "POST" }
    );

    const reader = response.body?.getReader();
    const decoder = new TextDecoder();
    let aiContent = "";

    setMessages(prev => [...prev, { role: "assistant", content: "" }]);

    while (reader) {
      const { done, value } = await reader.read();
      if (done) break;
      aiContent += decoder.decode(value);
      setMessages(prev => {
        const newMsgs = [...prev];
        newMsgs[newMsgs.length - 1] = { role: "assistant", content: aiContent };
        return newMsgs;
      });
    }
    setLoading(false);
  };

  return (
    <div className="max-w-2xl mx-auto p-4">
      <h1 className="text-2xl font-bold mb-4">AI Workspace</h1>

      <div className="space-y-4 mb-4 min-h-[400px] border rounded p-4">
        {messages.map((msg, i) => (
          <div key={i} className={msg.role === "user" ? "text-right" : "text-left"}>
            <div className={`inline-block p-3 rounded-lg ${
              msg.role === "user" ? "bg-blue-500 text-white" : "bg-gray-100"
            }`}>
              {msg.content}
            </div>
          </div>
        ))}
        {loading && <div className="text-gray-400">AI 正在思考...</div>}
      </div>

      <div className="flex gap-2">
        <input
          value={input}
          onChange={(e) => setInput(e.target.value)}
          onKeyDown={(e) => e.key === "Enter" && sendMessage()}
          placeholder="输入消息..."
          className="flex-1 border rounded px-4 py-2"
        />
        <button
          onClick={sendMessage}
          disabled={loading}
          className="bg-blue-500 text-white px-6 py-2 rounded hover:bg-blue-600 disabled:opacity-50"
        >
          发送
        </button>
      </div>
    </div>
  );
}
```

## 六、第 3 步：多轮对话记忆

> 本步目标：让 AI “记住”前面说过的话——你告诉它“我叫赵亮”，再问“我叫什么”，它能答上来。

### 6.1 先看现在的问题（花 30 秒体验一下）

用现在的程序做个测试：

1. 问：“我叫赵亮，请记住”
2. 再问：“我叫什么名字？”
3. AI 答不上来 ❌

这不是 bug，是大模型的特性：**模型本身没有记忆**，每次 API 调用都是独立的，它只能看到你这一次发过去的那一句话。

### 6.2 解决思路（行业标准做法）

记忆不靠模型，靠我们自己的程序：**前端把整份聊天记录一起发给后端，后端原样转给大模型**。模型每次都能看到完整的历史，自然就能“接上话”了。

```
第1轮：[用户:我叫赵亮]                              → AI: 你好赵亮
第2轮：[用户:我叫赵亮, AI:你好赵亮, 用户:我叫什么]   → AI: 你叫赵亮 ✅
```

### 6.3 改后端：`backend/app/main.py`（用 PyCharm）

**改动目标**：原来接口只收一句话（`message`），改成收完整对话历史数组（`messages`）。

**① 在文件顶部加一行 import**（和其他 import 放一起）：

```python
from pydantic import BaseModel
```

**② 在 `client = OpenAI(...)` 那段之后、`@app.post("/api/chat")` 之前，加一个数据模型定义**：

```python
class ChatRequest(BaseModel):
    messages: list  # 接收前端发来的完整对话历史
```

**③ 把原来的 `@app.post("/api/chat")` 整个函数替换成**：

```python
@app.post("/api/chat")
async def chat(req: ChatRequest):
    """流式对话接口（支持多轮上下文）"""
    def generate():
        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=req.messages,   # ← 核心改动：把整个历史传给模型（原来只传一句话）
            stream=True
        )
        for chunk in response:
            if chunk.choices[0].delta.content:
                yield chunk.choices[0].delta.content

    return StreamingResponse(generate(), media_type="text/plain")
```

> 💡 pydantic 是什么？
>
> FastAPI 自带的库，用来定义“接口要收什么形状的数据”。类比前端的 TypeScript：
>
> ```ts
> interface ChatRequest { messages: { role: string; content: string }[] }
> ```
>
> 如果前端发的数据形状不对，FastAPI 会自动返回 422 错误，不会让脏数据进入你的代码。

保存文件后，后端开了 `--reload` 会自动重启。**看一眼前端终端（PyCharm Terminal）**：重新出现 `Application startup complete` = 重启成功；如果出现红色报错 = 代码改错了，对照上面检查。

### 6.4 改前端：`frontend/src/app/page.tsx`（用 VSCode）

**改动目标**：原来只发当前这一句话（`?message=xxx`），改成把完整聊天记录以 JSON 格式发给后端。

**具体操作**：打开 `src/app/page.tsx`，找到 `sendMessage` 函数，**整个替换成**下面这份（函数前面的 `const sendMessage = async () => {` 到最后的 `};` 全部换掉，函数外面的代码不动）：

```tsx
const sendMessage = async () => {
  if (!input.trim()) return;

  const userMsg = { role: "user", content: input };
  const newMessages = [...messages, userMsg];  // ← 改动1：先算出包含本句话的完整历史
  setMessages(newMessages);
  setInput("");
  setLoading(true);

  const response = await fetch("http://localhost:8000/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },  // ← 改动2：告诉后端我发的是 JSON（必须有）
    body: JSON.stringify({ messages: newMessages }),   // ← 改动3：发完整历史，不再用 ?message= 参数
  });

  const reader = response.body?.getReader();
  const decoder = new TextDecoder();
  let aiContent = "";

  setMessages(prev => [...prev, { role: "assistant", content: "" }]);

  while (reader) {
    const { done, value } = await reader.read();
    if (done) break;
    aiContent += decoder.decode(value);
    setMessages(prev => {
      const newMsgs = [...prev];
      newMsgs[newMsgs.length - 1] = { role: "assistant", content: aiContent };
      return newMsgs;
    });
  }
  setLoading(false);
};
```

> 💡 三处改动，本质就一件事：从“发一句话”变成“发完整历史”。请求方式也从 URL 参数换成了 JSON body——POST 传复杂数据的标准方式，你做前端应该很熟。
>
> ⚠️ 注意：原来 URL 后面的 `?message=` 参数要**删掉**，现在数据放在 body 里。

**② 在 `client = OpenAI(...)` 那段之后、接口定义之前，加上传目录配置**：

```python
UPLOAD_DIR = os.path.join(os.path.dirname(__file__), "..", "uploads")  # backend/uploads/ 目录
os.makedirs(UPLOAD_DIR, exist_ok=True)  # 目录不存在就自动创建，存在也不报错
ALLOWED_EXT = [".txt", ".md", ".pdf"]  # 只允许上传这三种格式
```

**③ 在文件末尾新增上传接口**（和 `/api/chat` 并列）：

```python
@app.post("/api/upload")
async def upload(file: UploadFile = File(...)):
    """文档上传接口"""
    # 1. 校验文件类型
    ext = os.path.splitext(file.filename)[1].lower()  # 取后缀，如 ".txt"
    if ext not in ALLOWED_EXT:
        raise HTTPException(status_code=400, detail=f"不支持的文件类型: {ext}")

    # 2. 生成随机文件名，防止同名文件互相覆盖（原名返回给前端展示用）
    save_name = f"{uuid.uuid4().hex}{ext}"
    save_path = os.path.join(UPLOAD_DIR, save_name)

    # 3. 写入磁盘（"wb" = 以二进制写入，文件上传必须用二进制）
    content = await file.read()
    with open(save_path, "wb") as f:
        f.write(content)

    return {"filename": file.filename, "saved_as": save_name, "size": len(content)}
```

> 💡 `raise HTTPException(...)` 是 FastAPI 报错的标准方式：前端会收到 400 状态码和 detail 里的错误信息。类似前端请求里 `if (res.code !== 0) throw new Error(...)` 的后端版。

```tsx
const handleUpload = async (e: React.ChangeEvent<HTMLInputElement>) => {
  const file = e.target.files?.[0];
  if (!file) return;

  setUploading(true);
  const formData = new FormData();
  formData.append("file", file);  // "file" 这个名字要和后端 UploadFile 的参数名一致

  const res = await fetch("http://localhost:8000/api/upload", {
    method: "POST",
    body: formData,  // ⚠️ 注意：发 FormData 千万不要手动设置 Content-Type！
  });

  if (!res.ok) {
    const err = await res.json();
    alert(err.detail);  // 后端返回的错误信息，比如“不支持的文件类型”
  } else {
    const data = await res.json();
    setFiles(prev => [...prev, data.filename]);
  }

  setUploading(false);
  e.target.value = "";  // 清空 input，允许再次选择同一个文件
};
```

> ⚠️ 重点：发 FormData 时**不要写 `headers: { "Content-Type": ... }`**。浏览器会自动生成带边界（boundary）的 Content-Type，手动设置反而会把它盖掉，后端解析不了直接报错。这是前端上传的经典坑。

### 8.1 先看问题：为什么 AI 答不了“年假几天”

现在你去问 AI“公司年假几天”，它只能瞎猜或者编一个。原因有两个：

1. **大模型的知识有截止日期**，而且是训练时学的公开知识，不可能知道你们公司的制度。
2. **它没见过你上传的文档**。第 4 步的文件只是躺在 `uploads/` 目录里，和 AI 毫无关系。

那把整篇文档发给模型行不行？小文档勉强可以，但：

- 大模型有 **Token 上限**（输入长度限制），几十页的文档直接塞不下；
- 每次提问都带全文，**又贵又慢**（按 Token 计费）；
- 资料太长时模型会“迷失”，答非所问。

行业的标准解法叫 **RAG（Retrieval-Augmented Generation，检索增强生成）**：

> 不把所有知识塞给模型，而是**提问时先检索出最相关的一小段**，只把这一小段交给模型参考。

```
上传时（入库）：
  文档 → 提取文字 → 切成小段（切片）→ 每段转成向量 → 存入向量数据库（Chroma）

提问时（检索）：
  用户提问 → 问题也转成向量 → 在向量库里找最相似的 3 段 → 拼进提示词 → 模型基于资料回答 ✅
```

类比图书馆：入库 = 把书拆成卡片放进索引柜；提问 = 按关键词抽出最相关的几张卡片，带着卡片去答题。你不需要背下整个图书馆。

### 8.2 三个核心概念（彻底搞懂再动手）

**① Embedding（嵌入）和向量**

> 文本没法直接比较“像不像”，所以先用一个**嵌入模型（Embedding 模型）**，把一段文字变成一串数字（比如 384 个浮点数），叫**向量**。神奇之处在于：**意思相近的文字，向量在数学上也相近**。“年假制度”和“带薪休假”的向量会很接近，和“今天吃什么”的向量则离得很远。  
> 类比：每段文字被标注到一个多维坐标系的某个点上，语义相近 = 坐标相近。这个“翻译器”我们不用自己写，Chroma 内置了一个，调 `collection.add()` 时自动调用。  
> **② 向量数据库和相似度检索**  
> 普通数据库按精确匹配查（`WHERE name = 'xxx'`），向量数据库按**距离**查：拿问题的向量和库里所有向量比距离，返回最近的几条（常用余弦相似度）。我们用 **Chroma**：零配置，数据存本地文件夹，跟 SQLite 一个思路。  
> 这也是为什么用户问“假期怎么休”也能命中写着“年假制度”的切片——**语义检索，不是关键词匹配**，这是 RAG 和传统搜索的本质区别。  
> **③ 为什么要切片（Chunking）**  
> 一篇长文要切成 300 字左右的小段再向量化。因为向量是“一整段话的语义浓缩”：一篇万字文档变成一个向量，语义被搅和在一起，检索精度会很差；切成小段后，每段的向量只表达那一小段的意思，检索才准。相邻切片留一点重叠（overlap），防止一句话被拦腰截断。  
> **面试加餐：RAG 和微调（Fine-tuning）的区别？**  
> 微调 = 重新训练模型把知识学进去，贵、慢、知识更新要重训；RAG = 知识存在外部库里，检索后拼进提示词，便宜、实时可更新、还能标注来源。企业知识库场景几乎都用 RAG。

```python
def extract_text(content: bytes, ext: str) -> str:
    """从文件内容（字节）提取纯文字，不依赖磁盘文件"""
    if ext == ".pdf":
        reader = PdfReader(io.BytesIO(content))  # BytesIO：把字节包装成内存中的“假文件”给 pypdf 读
        return "\n".join((page.extract_text() or "") for page in reader.pages)
    return content.decode("utf-8", errors="ignore")  # errors="ignore"：遇到编码怪异的字节直接跳过，不崩

def split_text(text: str) -> list:
    """长文切片：每片最多 CHUNK_SIZE 字，相邻两片重叠 CHUNK_OVERLAP 字"""
    text = text.replace("\n", " ")   # 换行压成空格，避免列表、标题被拆散后语义断裂
    chunks = []
    start = 0
    while start < len(text):
        end = start + CHUNK_SIZE
        chunk = text[start:end]
        if chunk.strip():            # 纯空白片段跳过（如文件末尾）
            chunks.append(chunk)
        start = end - CHUNK_OVERLAP  # 往回退 overlap 长度，保证重叠区内容不丢（见 8.2 ③）
    return chunks
```

> 💡 这两个函数对应 8.1 图里“入库”链路的前两步：提取文字、切片。第三步“转向量”不用写代码，`collection.add()` 自动完成。  
> 切片算法是“滑动窗口”：取 0~~300 字为第 1 片，然后从 250 字开始取第 2 片（250~~550），以此类推——所以相邻两片有 50 字重叠。

```python

    content = await file.read()
    content_hash = hashlib.md5(content).hexdigest()

    # 3. 先提取文字、切片：提不出内容就直接拒收，文件不落盘（顺序是关键）
    text = extract_text(content, ext)   # 注意：传的是 content 字节，不再是路径（对应 ③ 的新签名）
    chunks = split_text(text)
    if not chunks:
        raise HTTPException(status_code=400, detail="未能提取到文字，可能是图片型/扫描件文件，暂不支持")

    # 4. 校验通过，才写盘：用指纹作为磁盘文件名，同内容重复上传只覆盖同一个文件
    save_name = f"{content_hash}{ext}"
    save_path = os.path.join(UPLOAD_DIR, save_name)
    with open(save_path, "wb") as f:
        f.write(content)

    # 5. 入库知识库（向量化由 collection.upsert 自动完成）
    ids = [f"{content_hash}-{i}" for i in range(len(chunks))]

    collection.upsert(
        documents=chunks,
        ids=ids,
        metadatas=[{"filename": file.filename}] * len(chunks),  # 附带元数据：原始文件名（第 6 步引用溯源要用）
    )

            "duplicated": duplicated}
```

> 💡 这段代码的三个关键设计：
>
> 1. **`collection.upsert()` 三件套**：`documents` 存内容、`ids` 是唯一主键、`metadatas` 存额外信息（不参与检索，查询时原样带回）。类比关系型数据库：文档 = 字段值，id = 主键，metadata = 其他列。`upsert`（update + insert）和 `add` 的区别：`add` 遇到已存在的 ID 会报错，`upsert` 就地更新——所以重复上传不报错也不重复。
> 2. **内容哈希去重**：不用“哪次上传”（随机名）标识文件，改用“内容本身”（MD5 指纹）——相同内容指纹必相同，磁盘文件名和切片 id 都用指纹，重复上传自然撞上同一批 id，实现**幂等**（传多少次结果都一样）。这和前端打包产物文件名带 hash、缓存 ETag 是同一个思路：内容寻址。选 MD5 不选 SHA-256，因为目的是内容寻址而非密码学安全，MD5 更快更短。注意：去重只防“相同内容重复传”，**修改内容**后再传是新指纹，新旧版本会共存，按文件名覆盖更新是后续优化项。
> 3. **先校验后落盘（无副作用失败）**：提取、切片这类“内容能不能用”的校验放在写盘之前，不合格直接 400 拒收——磁盘不会留下垃圾文件，库里不会进脏数据，用户当场就知道原因（前端第 4 步写的错误弹窗分支自动接住）。这是文件上传类接口的最佳实践，术语叫**失败无副作用**。  
>    **⑤ 改对话接口：回答前先检索**。把整个 `/api/chat` 函数替换成：

```python
@app.post("/api/chat")
async def chat(req: ChatRequest):
    """流式对话接口（支持多轮上下文 + 知识库检索）"""
    messages = req.messages

    # ===== RAG 核心 1：检索 =====
    # 用用户最新一句话去知识库里找最相关的 3 个切片（问题自动转向量、自动比距离）
    if collection.count() > 0:          # 知识库里有文档才检索，空的直接跳过，避免报错
        last_question = messages[-1]["content"]
        # include 参数：除了文档原文，把“距离”也返回回来（距离越小越相关）
        results = collection.query(
            query_texts=[last_question],
            n_results=3,
            include=["documents", "distances"]
        )
        # 相关性过滤：只保留距离 < 1.2 的切片，无关问题（如闲聊）会被全部过滤掉（阈值是经验值，可自行调）
        retrieved = [
            doc for doc, dist in zip(results["documents"][0], results["distances"][0])
            if doc and doc.strip() and dist < 1.2
        ]
    else:
        retrieved = []

    # ===== RAG 核心 2：拼提示词 =====
    # 检索到资料，就以 system 消息的身份放在对话历史最前面（模型会把它当“背景知识”）
    if retrieved:
        context = "\n\n".join(retrieved)
        system_prompt = (
            "你是企业知识库助手。以下是参考资料：\n\n"
            f"{context}\n\n"
            "请基于以上参考资料回答用户问题。"
            "如果资料中没有相关内容，请如实说‘知识库中未提及’，不要编造。"
        )
        messages = [{"role": "system", "content": system_prompt}] + messages

    def generate():
        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=messages,   # 注意：用的是拼好资料的 messages，不是 req.messages
            stream=True
        )
        for chunk in response:
            if chunk.choices[0].delta.content:
                yield chunk.choices[0].delta.content

    return StreamingResponse(generate(), media_type="text/plain")
```

> 💡 三个新知识点：
>
> 1. **`system` 角色**：第 3 步说过 role 有 user / assistant / system 三种。system 消息不对用户展示，用来给模型“立规矩、垫背景”。RAG 检索到的资料就是垫在这里。
> 2. **“不要编造”这句提示词不是废话**：大模型天生爱“一本正经地胡说”（术语叫**幻觉**），明确要求它基于资料回答、不知道就说不知道，是 RAG 工程的标配。
> 3. **距离阈值过滤**：向量检索永远会返回“最接近的 N 条”，哪怕毫不相关——不过滤的话闲聊也会被注入知识库人设。让 `query` 连距离一起返回，距离超阈值的丢弃，这是生产环境控制检索相关性的标准做法，面试必问。  
>    保存后 `--reload` 自动重启。**看后端终端**：如果出现红色报错（比如 sqlite3 版本问题），对照 8.8 的坑表处理。

### 8.9 面试知识点（这步的问答频率最高，背熟）

**问：什么是 RAG？解决什么问题？**

> RAG = 检索增强生成。大模型有知识截止、不了解私有数据、容易幻觉三个问题；RAG 在提问时先从知识库检索相关内容，拼进提示词让模型基于资料回答，知识可实时更新、可追溯来源，是企业知识库的标准方案。  
> **问：什么是 Embedding？**  
> 用嵌入模型把文本映射成高维向量，语义相近的文本向量距离近。提问和文档都转向量后，用余弦相似度找最近邻，就实现了语义检索（区别于关键词匹配）。  
> **问：为什么要切片？怎么切？**  
> 向量是整段文本的语义浓缩，文档太长会稀释语义、检索不准，也有 Token 上限问题。实践按固定长度滑窗切（300 字左右），相邻片留 50 字重叠防截断。更精细的做法是按段落/标题的语义切。  
> **问：检索到不相关内容怎么办？**  
> 可以设相似度阈值，距离太远就不采用；同时在提示词里要求模型“资料没有就说不知道”，双保险压幻觉。这也是第 6 步引用溯源的基础：回答标注来自哪份文档，用户可自行验证。

### 9.1 为什么必须做引用溯源（先想明白价值）

没有溯源的知识库有三个硬伤：

1. **不可验证**：用户不知道答案是来自文档还是模型编的，不敢信；
2. **出错无法定位**：答错了不知道是哪份文档、哪个切片的问题，没法修；
3. **责任不清**：企业场景里“AI 说的”不能作为依据，“出自《员工手册》第几条”才可以。

做完这步，压幻觉的手段集齐三件套：**提示词约束**（第 5 步）+ **阈值过滤**（第 5 步）+ **来源可验证**（本步）——面试讲幻觉治理时按这个顺序说。

### 9.2 三个核心概念（本步的知识主线）

**① SSE（Server-Sent Events）：带类型的流**

现在的 `/api/chat` 返回的是裸文字流（`text/plain`），只有一种内容。但“引用来源”是结构化数据（JSON），不能混进文字流——你没法分辨收到的 `[{...}]` 是来源还是回答的一部分。

SSE 在流之上加了消息结构：

```
event: sources
data: [{"id":1,"filename":"公司制度.txt","snippet":"..."}]

event: token
data: {"content":"入"}

event: token
data: {"content":"职"}

event: done
data: {}
```

规则：每条消息由 `event:`（类型）和 `data:`（内容）组成，**空行是消息边界**。Content-Type 是 `text/event-stream`。前端按类型分发：`sources` 渲染引用卡片，`token` 追加文字，`done` 结束。

> 💡 为什么 `data` 里包 JSON 而不是裸文字？因为回答的 token 可能含换行符，而 SSE 里换行有特殊含义（分隔 data 行）——裸文字会撕裂消息帧。`json.dumps` 会把 `\n` 转义成 `\\n`，天然安全。DeepSeek/OpenAI 的官方流式接口也是这个格式（`data: {...}`，最后 `data: [DONE]`）。

**② metadata 兑现：每个切片自带的“出身证明”**

第 5 步入库时存了 `metadatas=[{"filename": ...}]`，当时说“第 6 步要用”。现在检索时把 `include` 加个 `"metadatas"`，每个切片就会带回自己的文件名——溯源的原料早准备好了。

**③ 编号引用：提示词 + 来源列表的配合**

拼提示词时给每段资料编号：`[1] (来自: 公司制度.txt) 内容...`，并要求模型“引用时在句尾标 [1]”。同时把同样的编号列表发给前端渲染卡片——**模型标的号和前端卡片的号必须是同一套编号**，这是全链路设计的核心：后端一处编号，提示词和前端都消费它。

### 9.3 依赖：零新增（本步不装任何包）

`json` 是 Python 标准库，SSE 就是普通 HTTP 响应——本步是纯代码改造，体会一下“协议升级不等于弓新依赖”。

```python
@app.post("/api/chat")
async def chat(req: ChatRequest):
    """流式对话接口（SSE：sources / token / done 三种事件）"""
    messages = req.messages

    # ===== RAG 核心 1：检索（include 新增 metadatas，把文件名带回来）=====
    if collection.count() > 0:
        last_question = messages[-1]["content"]
        results = collection.query(
            query_texts=[last_question],
            n_results=3,
            include=["documents", "distances", "metadatas"]   # ← 新增 metadatas
        )
        # 阈值过滤照旧，只是连 metadata 一起打包成 (文档, 元数据) 元组
        hits = [
            (doc, meta) for doc, dist, meta in zip(
                results["documents"][0], results["distances"][0], results["metadatas"][0])
            if doc and doc.strip() and dist < 1.2
        ]
    else:
        hits = []

    # ===== 新增：构建编号引用源（按“文件名+内容”去重，重复切片只算一条来源）=====
    sources = []          # 发给前端的卡片列表：[{id, filename, snippet}]
    context_parts = []    # 拼进提示词的编号资料：[1] (来自: xx) 内容...
    seen = set()
    for doc, meta in hits:
        key = (meta.get("filename"), doc)
        if key in seen:
            continue
        seen.add(key)
        sources.append({"id": len(sources) + 1, "filename": meta.get("filename", "未知来源"), "snippet": doc})
        context_parts.append(f"[{len(sources)}] (来自: {meta.get('filename', '未知来源')})\n{doc}")

    # ===== RAG 核心 2：拼提示词（升级为“编号版”，并要求模型标注引用）=====
    if sources:
        context = "\n\n".join(context_parts)
        system_prompt = (
            "你是企业知识库助手。以下是参考资料，每条以编号开头：\n\n"
            f"{context}\n\n"
            "请基于以上参考资料回答用户问题。要求：\n"
            "1. 在引用了资料的句子末尾标注资料编号，如 [1]，编号只能来自上述资料；\n"
            "2. 如果资料中没有相关内容，请如实说‘知识库中未提及’，不要编造。"
        )
        messages = [{"role": "system", "content": system_prompt}] + messages

    def generate():
        # ① 先发 sources 事件：结构化数据单独一条消息，先于正文到达，前端可提前渲染卡片
        if sources:
            yield f"event: sources\ndata: {json.dumps(sources, ensure_ascii=False)}\n\n"

        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=messages,
            stream=True
        )
        # ② 逐字流式：每个 token 包成一条 token 事件（JSON 转义保证换行不撕裂消息帧）
        for chunk in response:
            if chunk.choices[0].delta.content:
                piece = chunk.choices[0].delta.content
                yield f"event: token\ndata: {json.dumps({'content': piece}, ensure_ascii=False)}\n\n"

        # ③ 结束事件：明确告诉前端流结束了（不依赖连接断开来判断）
        yield "event: done\ndata: {}\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream")   # ← text/plain 换掉了
```

> 💡 这段代码的三个关键设计：
>
> 1. **一处编号，三处消费**：`sources` 列表的 id 同时出现在——提示词的资料编号、模型回答里的 [n]、前端卡片——三者能对齐全靠后端这一处统一编号。
> 2. **`ensure_ascii=False`**：默认会把中文转成 `\u516c\u53f8` 这种转义，功能不受影响但 DevTools 里没法直接读；关掉后 `data` 里就是可读中文，调试体验天壤之别。
> 3. **done 事件的意义**：前端不应该靠“连接断了”猜结束——网络抖动也会断。显式的结束事件是流式协议的标配设计（OpenAI 的 `data: [DONE]` 同理）。
>
> ⚠️ 替换后先别急着测前端，先用 curl 验后端（见 9.6 场景 1），确认流的格式对了再动前端。

### 9.5 改前端：`frontend/src/app/page.tsx`（三处）

**① 消息类型加 `sources` 字段**（文件开头附近）：

把 `const [messages, setMessages] = useState<{role: string, content: string}[]>([]);` 换成：

```tsx
type Source = { id: number; filename: string; snippet: string };
type Msg = { role: string; content: string; sources?: Source[] };

// 组件内：
const [messages, setMessages] = useState<Msg[]>([]);
```

**② 升级 `sendMessage` 的流式解析段**：把从 `const reader = response.body?.getReader();` 到 `setLoading(false);` 之间（含这两行）替换成：

```tsx
    const reader = response.body?.getReader();
    const decoder = new TextDecoder();
    let aiContent = "";
    let buffer = "";   // SSE 缓冲区：网络分包和消息边界不对齐，必须攒够一条完整消息再解析

    setMessages(prev => [...prev, { role: "assistant", content: "" }]);

    while (reader) {
      const { done, value } = await reader.read();
      if (done) break;
      buffer += decoder.decode(value, { stream: true });   // stream:true 防中文被拦腰截成乱码（多字节字符）

      // 一条完整的 SSE 消息以空行 "\n\n" 结束；最后一段可能不完整，留在 buffer 里等下一轮
      const events = buffer.split("\n\n");
      buffer = events.pop() ?? "";

      for (const evt of events) {
        if (!evt.trim()) continue;
        let name = "";
        let data = "";
        for (const line of evt.split("\n")) {
          if (line.startsWith("event:")) name = line.slice(6).trim();
          else if (line.startsWith("data:")) data = line.slice(5).trim();
        }
        if (!data) continue;
        const payload = JSON.parse(data);

        if (name === "sources") {
          // 来源事件：写进当前 AI 消息的 sources 字段（卡片会立刻渲染出来，不用等回答完成）
          setMessages(prev => {
            const next = [...prev];
            next[next.length - 1] = { ...next[next.length - 1], sources: payload };
            return next;
          });
        } else if (name === "token") {
          aiContent += payload.content;
          setMessages(prev => {
            const next = [...prev];
            next[next.length - 1] = { ...next[next.length - 1], content: aiContent };
            return next;
          });
        }
        // done 事件：无需处理，流结束后下面会重置 loading
      }
    }
    setLoading(false);
```

> 💡 这段里藏着一个前端流式开发的经典坑：**buffer 机制**。`reader.read()` 返回的网络块和 SSE 消息边界完全不对齐——一条消息可能被勈成两个块，一个块里也可能有三条消息。所以必须攒进 buffer、按 `\n\n` 切、把不完整的尾巴留着。你以前用 WebSocket 没遇到过这个问题，因为 WebSocket 天然按消息分帧；HTTP 流没有这个待遇，要自己拼。
>
> 另一个坑：`decoder.decode(value, { stream: true })` 的 `stream: true` 不能省。中文在 UTF-8 里占 3 个字节，网络块可能从中间截断，不加这个参数会把半个汉字解码成乱码 `\uFFFD`。

**③ 渲染引用卡片**：把消息列表的 `{msg.content}` 所在的那个气泡容器后面（`</div>` 闭合后、外层 `<div key={i}>` 闭合前）加一段：

```tsx
            {msg.sources && msg.sources.length > 0 && (
              <div className="mt-2 text-xs text-gray-500 space-y-1 max-w-md">
                {msg.sources.map(s => (
                  <details key={s.id} className="bg-gray-50 border rounded px-2 py-1">
                    <summary className="cursor-pointer select-none">
                      [{s.id}] {s.filename}
                    </summary>
                    <div className="mt-1 whitespace-pre-wrap leading-relaxed">{s.snippet}</div>
                  </details>
                ))}
              </div>
            )}
```

> 💡 `<details>/<summary>` 是浏览器原生的折叠组件，零 JS、零状态——点击展开/收起完全由浏览器接管。这种“能用原生标签就不写状态”的习惯，面试官看到会加分。
>
> 注意消息渲染处的类型：现在 `messages.map((msg, i) => ...)` 里的 `msg` 自动获得 `Msg` 类型（因为 useState 的泛型换了），直接用 `msg.sources` 不会报错。
>
> 回答正文里的 `[1]` 标记会原样显示在气泡里——暂不做高亮渲染，先把链路跑通，“把 [n] 渲染成可点击的样式”列为后续优化项。

### 9.7 常见坑（本步的坑集中在“流的解析”上）

| 现象                  | 原因与解决                                                   |
| ------------------- | ------------------------------------------------------- |
| 前端报 `JSON.parse` 错误 | 没做 buffer，半条消息就解析了。对照 9.5 ② 的 buffer 机制逐行检查             |
| 中文乱码 `\uFFFD`       | `decoder.decode` 没加 `{ stream: true }`                  |
| 回答里的 [3] 没有对应卡片     | 模型编造了不存在的编号（提示词没压住）。属模型行为，前端可忽略越界编号；优化项：后端校验后再转发        |
| 卡片里文件名是“未知来源”       | 入库时没存 metadata（比如清空过知识库后的旧切片）。重传一次文档即可                  |
| Swagger 里测 chat 很别扭 | event-stream 在 Swagger 里展示不友好，用 curl 或前端测               |
| sources 事件没到前端      | 检查知识库是否为空、阈值是否全滤掉了（后端终端加一行 `print(sources)` 看）          |
| 部署后流式失效（以后会遇到）      | Nginx 默认缓冲响应，需加 `proxy_buffering off`——部署步骤（第 10 步）时的伏笔 |
| 卡片展开后换行丢了一半         | 忘了 `whitespace-pre-wrap`，原文里的换行会被 HTML 折叠               |

### 9.8 面试知识点（本步能把“玩具项目”和“产品”区分开）

**问：RAG 怎么做引用溯源？**

> 入库时把来源信息（文件名）存进切片的 metadata；检索时连 metadata 一起取回；拼提示词时给每段资料编号，并要求模型引用时标注编号；同时把编号来源列表通过 SSE 单独事件发给前端渲染。后端一处编号、提示词和前端两处消费，三者对齐。还能加一层校验：模型引用了不存在的编号就剔除。

**问：为什么用 SSE？和 WebSocket 什么区别？**

> LLM 流式回答是单向的（服务端→客户端），SSE 基于普通 HTTP、天然支持重连和代理穿透，够用且更简单；WebSocket 是全双工，适合聊天室这类双向场景。流式输出选 SSE 是行业惯例（OpenAI/DeepSeek 都是）。
>
> **追问：那为什么前端不用浏览器原生的 EventSource？**  
> 因为 EventSource 只支持 GET 请求，而我们的对话要 POST 带历史消息，所以用 fetch 手动解析 SSE 流——这也是为什么主流 AI 产品的前端都是自己写解析器。

**问：模型乱标引用编号怎么办？**

> 三道防线：提示词明确约束“编号只能来自上述资料”；降低单次引用的资料条数（资料越少越不容易标错）；前端/后端做越界校验，忽略或剔除不存在的编号。本质是模型的概率性行为，只能约束不能根除，工程上要有兜底。
>
> **问：同一份文档多个切片命中，来源列表怎么处理？**  
> 按“文件名+内容”去重后编号；更产品化的做法是按文件聚合，一个文件一张卡片，里面列出多个命中片段。
>
> **问：为什么 data 里包 JSON？**  
> 因为 token 可能含换行符，而 SSE 里换行是消息帧的分隔符，裸文字会撕裂消息；JSON 转义天然规避，还能携带结构化字段。
>
> **问：前端解析流为什么要 buffer？**  
> HTTP 流的网络分包和消息边界不对齐（一个块里可能有多条消息，一条消息也可能被勈在两个块里），必须按 `\n\n` 切完整消息、不完整的尾巴攒到下一轮。WebSocket 没这个问题是因为它天然按消息分帧。

## 十、第 7 步：Agent + Tool Calling（引入 LangChain，对比手写版）

> 本步目标：把“检索知识库”这个能力作为**工具**交给模型，由**模型自己判断**要不要查；手写实现一版，再用 LangChain 实现一版，两版对照。
>
> 预计耗时：2.5 小时（其中 40 分钟建议用来读 10.1、10.2）。改动：装 2 个包 + 后端 `main.py`，**前端一行不用改**。
>
> 这一步是全项目的质变点：从“按剧本执行的程序”变成“会自己做决定的智能体”。面试高频问题“RAG 和 Agent 的区别”就是从这一步来的。

### 10.1 先回顾痛点（为什么要做这一步）

回看第 5 步踩过的两个坑：

| 案例            | 当时的现象             | 根因                   |
| ------------- | ----------------- | -------------------- |
| “介绍下你自己”答出怪话  | 命中“我是你的主人，我叫赵亮”切片 | 代码每次都无脑查知识库，模型没有选择权  |
| “我在找什么样的工作”答错 | 命中“实践项目”干扰切片      | 代码只会比向量距离，判断不了“该不该查” |
| 阈值 1.1        | 靠实测数据调出来          | 本质是给“写死的流程”打补丁       |

当时的检索逻辑是**写死的流水线**：

```
用户提问 → 无条件检索 → 阈值过滤 → 拼提示词 → 生成回答（模型全程被动）
```

当时讲过查询路由的三档方案：① 检索后阈值（第 5 步已完成）② 路由层（加一次分诊调用）③ Function Calling（模型自主决定）。**这一步直接升到第三档**：模型先看到问题，自己判断——“这是问公司制度的，我要查知识库”“这是闲聊，我直接答”。

### 10.2 三个核心概念（花 40 分钟读透再动手）

**① Tool Calling 的完整消息流（本步的知识主线）**

你给模型一份“工具说明书”（工具名、干什么用、参数是什么），模型遇到自己答不了的问题时，返回的**不是回答文字，而是一个结构化的调用意图**。一次用户提问，实际要调**两次** API：

```
第 1 次调用（决策）：
  你 → 模型：对话历史 + 工具清单（含“搜知识库”的说明书）
  模型 → 你：我不直接回答，我要调用 search_knowledge_base(query="年假制度")   ← 只是意图，什么都没执行！

你的程序执行：
  解析意图 → 真的去 Chroma 检索 → 拿到结果（执行权始终在你的代码手里）

第 2 次调用（生成）：
  你 → 模型：原对话历史 + assistant 的调用意图 + tool 角色的执行结果（流式）
  模型 → 你：基于检索结果的正式回答 ✅
```

第 2 次请求的 messages 数组长这样（注意**四种角色**都登场了）：

```
[ {role: "system",     content: 人格},
  {role: "user",       content: "年假几天？"},
  {role: "assistant",  tool_calls: [{id, function: {name, arguments}}]},  ← 模型的调用意图，原样回填
  {role: "tool",       tool_call_id: 对应上面的 id, content: 检索结果} ]   ← 你执行后的结果
```

> 💡 类比前端调后端接口：浏览器从不自己碰数据库，只发结构化请求，真正执行的是服务端。Tool Calling 里，**大模型变成了“发请求的浏览器”，你的后端代码是“执行请求的服务端”**。模型只决策、不执行——这是安全边界，面试必问。
>
> ⚠️ 两个协议细节（写代码时会用到）：assistant 的 tool_calls 消息必须**原样回填**（OpenAI SDK 可以直接传回原始消息对象）；`tool` 角色消息必须带 `tool_call_id` 和调用意图配对，顺序不能乱，否则报 400。
>
> ⚠️ 成本观察点：每次提问从 1 次 API 调用变成 2 次（决策 + 生成），这是 Tool Calling 的固有成本。好处是决策调用不带长上下文、很短很便宜。

**② Agent = 思考-行动-观察的循环**

Tool Calling 是“单次调用工具”的能力；Agent 更进一步，是一个循环：

```
思考①：年假要查知识库    → 行动：调搜索工具    → 观察：得到“满一年5天”
思考②：入职3年，套制度算  → 行动：自己推理      → 观察：3年 → 5天
思考③：信息齐了          → 输出最终回答 ✅
```

一句话区分：**Tool Calling 是一种能力（模型会发调用意图），Agent 是一种架构（用循环让模型多次使用这个能力）**。本步先做 Tool Calling 打地基，第 8 步的 LangGraph 才是完整的多 Agent 编排——手册的顺序就是这么排的。

**③ LangChain 是什么 / 为什么“对比手写版”**

手写 Tool Calling 要处理的胶水代码：写工具描述 JSON → 解析模型返回的调用意图 → 执行 → 回填结果再请求。LangChain 把这些封装成了现成组件：

| 手写要做的         | LangChain 组件                                                 |
| ------------- | ------------------------------------------------------------ |
| 工具描述 JSON     | `@tool` 装饰器，写个普通 Python 函数，描述自动从 docstring 生成                |
| 解析调用意图        | 框架自动处理                                                       |
| “调用→回填→再请求”循环 | `AgentExecutor` 自动跑，还能自动多轮循环                                 |
| 连 DeepSeek    | `ChatOpenAI` 改个 base_url 就行（DeepSeek 兼容 OpenAI 格式，第 2 步就验证过） |

为什么手册强调“对比手写版”？很多人只会背“LangChain 的 Agent 怎么用”，而你是**先手写一整套（本步手写版），再用框架重做一遍**——你能回答面试官最想问的问题：“框架帮你封装了什么？手写时你在处理哪些脏活？什么时候框架反而是负担？”这种用过之后的判断力，比会用框架本身值钱。

> ⚠️ 提前预告 LangChain 版的两个代价（做的时候亲自体会）：引用卡片没了（框架不轻易暴露中间检索结果）、打字机效果没了（框架一把返回最终文本）。这不是你写错了，是抽象层的固有代价，10.9 有解释。

### 10.4 改后端（一）：把检索抽象成“工具”（`backend/app/main.py`）

**在 `PERSONA` 常量之后、`extract_text` 函数之前，加入下面两段**：

```python
# ===== 第 7 步：Tool Calling（让模型自己决定要不要查知识库）=====
# 工具描述 = 给模型看的“岗位说明书”：什么时候用、传什么参数，全写在这里。
# description 的措辞直接决定模型的调用准确率，这是工具设计的核心（见 10.9 坑 1）
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "search_knowledge_base",
            "description": (
                "检索企业知识库（用户上传的文档）。"
                "当用户的问题涉及公司制度、内部规定、工作事务或用户个人档案时，"
                "必须先调用本工具获取文档原文，不要凭自己的知识回答；"
                "与上述内容无关的常识问题和闲聊不要调用。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "query": {
                        "type": "string",
                        "description": "检索语句：把用户的问题改写成贴近文档措辞的查询"
                    }
                },
                "required": ["query"]
            }
        }
    }
]

def search_knowledge_base(query: str) -> list:
    """知识库检索工具的真正执行体（复用第 5 步检索逻辑：模型只负责决定调用，执行权始终在我们的代码手里）"""
    if collection.count() == 0:
        return []
    results = collection.query(
        query_texts=[query],
        n_results=3,
        include=["documents", "distances", "metadatas"]
    )
    # 阈值 1.1 保留为第二道防线：即使模型决定调工具，不相关的切片依然会被过滤（双保险）
    return [
        (doc, meta) for doc, dist, meta in zip(
            results["documents"][0], results["distances"][0], results["metadatas"][0])
        if doc and doc.strip() and dist < 1.1
    ]
```

💡 三个设计决策：

1. **description 里同时写了“什么时候用”和“什么时候不用”**。只写“检索知识库”的话，模型会什么都查（跟第 5 步的无脑流水线一个毛病）。明确排除“闲聊不要调用”，正是治好“介绍下你自己”怪答的关键。
2. **工具函数复用了第 5 步的检索逻辑**（含 1.1 阈值）。阈值从“唯一防线”降级成“第二道防线”——模型先做语义判断，漏网的不相关切片再被阈值拦住。这就是双保险架构。
3. **模型只决定调用，执行是我们的代码**：函数体内查的是我们自己的 `collection`，模型碰不到数据库，只能拿到我们返回的文本。安全边界清晰。

### 10.5 改后端（二）：手写 Tool Calling 版（本步核心，逐行读）

**把整个 `/api/chat` 函数替换成下面这版**（对照注释看每一段的作用）：

```python
@app.post("/api/chat")
async def chat(req: ChatRequest):
    """流式对话接口（第 7 步：Tool Calling 版；SSE 事件：tool / sources / token / error / done）"""
    messages = req.messages

    # ===== ① 决策调用（注意：不开流式！）=====
    # 必须先拿到完整返回，才能判断模型是“想调工具”还是“直接回答”，流式边收边判做不到也没必要（这次调用很短）
    base_messages = [{"role": "system", "content": PERSONA}] + messages
    try:
        decision = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=base_messages,
            tools=TOOLS,  # 把工具说明书交给模型，用不用由它决定（第 5 步的“无条件检索”在这里被彻底替换）
        )
    except Exception:
        # 决策阶段就失败：用标准 HTTP 错误返回（第 6.5 步的前端错误兜底会自动接住并提示用户）
        raise HTTPException(status_code=500, detail="模型服务暂时不可用，请稍后再试")

    choice = decision.choices[0].message
    tool_calls = getattr(choice, "tool_calls", None)  # 模型的调用意图（没有就是 None = 它决定直接答）
    print(f"[工具决策] {'调用 ' + tool_calls[0].function.name if tool_calls else '直接回答'}")  # 观察点：打在后端终端

    sources = []            # 引用卡片（第 6 步逻辑原样保留）
    final_messages = base_messages
    if tool_calls:
        # ===== ② 模型决定查知识库：解析参数 → 执行工具 → 结果回填对话 =====
        call = tool_calls[0]  # 我们只有一个工具，取第一个即可（多工具场景要循环处理）
        query = json.loads(call.function.arguments)["query"]  # 参数是 JSON 字符串，要反序列化（解析失败说明模型乱传，见 10.9 坑 3）
        hits = search_knowledge_base(query)

        # 构建编号资料和引用卡片（与第 6 步完全一致）
        context_parts = []
        seen = set()
        for doc, meta in hits:
            key = (meta.get("filename"), doc)
            if key in seen:
                continue
            seen.add(key)
            sources.append({"id": len(sources) + 1, "filename": meta.get("filename", "未知来源"), "snippet": doc})
            context_parts.append(f"[{len(sources)}] (来自: {meta.get('filename', '未知来源')})\n{doc}")

        if sources:
            tool_result = (
                "以下是检索到的知识库内容，按编号排列：\n\n"
                + "\n\n".join(context_parts)
                + "\n\n请基于以上内容回答。在引用了资料的句子末尾标注编号如 [1]；资料中没有的就如实说明。"
            )
        else:
            tool_result = "知识库中没有检索到和问题相关的内容。请如实告知用户知识库中没有相关资料。"

        # 按协议追加两条消息：assistant 的“调用意图” + tool 角色的“执行结果”（顺序不能乱，id 必须配对）
        final_messages = base_messages + [
            choice,  # OpenAI SDK 支持把原始消息对象（含 tool_calls 字段）直接传回去，不用手工拼 dict
            {"role": "tool", "tool_call_id": call.id, "content": tool_result}
        ]

    def generate():
        # ③ 决策透明事件：前端不认识这个事件名会自动忽略（只认 sources/token/error），纯粹用于观察和以后扩展
        yield f"event: tool\ndata: {json.dumps({'called': bool(tool_calls)}, ensure_ascii=False)}\n\n"
        if sources:
            yield f"event: sources\ndata: {json.dumps(sources, ensure_ascii=False)}\n\n"

        try:
            if tool_calls:
                # ④ 第二次调用（流式）：基于工具结果生成正式回答——打字机效果在这一步才有
                response = client.chat.completions.create(
                    model="deepseek-v4-flash",
                    messages=final_messages,
                    stream=True
                )
                for chunk in response:
                    if chunk.choices[0].delta.content:
                        piece = chunk.choices[0].delta.content
                        yield f"event: token\ndata: {json.dumps({'content': piece}, ensure_ascii=False)}\n\n"
            else:
                # 没调工具：决策调用已经拿到完整回答，整段一次吐出（无打字机效果，设计权衡见 10.9 坑 5）
                yield f"event: token\ndata: {json.dumps({'content': choice.content or ''}, ensure_ascii=False)}\n\n"
        except Exception:
            yield f"event: error\ndata: {json.dumps({'message': '模型服务暂时不可用，请稍后再试'}, ensure_ascii=False)}\n\n"

        yield "event: done\ndata: {}\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream")
```

💡 这段代码的四个关键设计：

1. **决策调用为什么不流式**：我们要先看完整返回，才能知道模型是想调工具还是直接回答。如果它决定调工具，流式吐出来的文字反而要丢弃。决策阶段要的是判断，不是展示。
2. **`tool` 事件是新加的**：记录“这次到底查没查知识库”。前端的解析器只认 `sources`/`token`/`error` 三种名字，遇到不认识的事件名直接跳过——所以**前端一行都不用改**（这是第 6 步 SSE 设计的红利，又一次兑现）。
3. **引用卡片链路完整保留**：工具执行结果里的编号 `[1]` 和发给前端的 sources 卡片是同一套编号（第 6 步“一处编号三处消费”的架构没变，只是编号的产生地移到了工具结果里）。
4. **阈值还在**：工具函数内部仍有 1.1 阈值过滤。模型判断 + 阈值过滤双保险，任何一道失手另一道兜底。

保存后 `--reload` 自动重启，确认终端无红色报错。

### 10.6 改后端（三）：LangChain 版（对照实现，体会框架的代价）

**① 文件顶部 import 区加四行**：

```python
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool as langchain_tool
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain.agents import create_tool_calling_agent, AgentExecutor
```

**② 在 `search_knowledge_base` 函数之后，加 LangChain 版的组件定义**：

```python
# ===== 第 7 步：LangChain 版 Agent（对照实现）=====
USE_LANGCHAIN = False  # 开关：改成 True 后 /api/chat 由 LangChain Agent 接管，用来对比两版的行为差异

# @tool 装饰器：把普通函数变成工具，工具描述直接从函数签名和 docstring 自动生成（手写版要写几十行 JSON）
@langchain_tool
def search_knowledge_base_lc(query: str) -> str:
    """检索企业知识库。当问题涉及公司制度、内部规定或用户个人档案时必须先调用本工具。"""
    hits = search_knowledge_base(query)  # 复用同一个执行体：两版只是“编排方式”不同，“能力”是同一个
    if not hits:
        return "知识库中没有检索到相关内容"
    parts = [f"[{i + 1}] (来自: {meta.get('filename', '未知来源')})\n{doc}" for i, (doc, meta) in enumerate(hits)]
    return "\n\n".join(parts)

lc_llm = ChatOpenAI(
    model="deepseek-v4-flash",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com",  # DeepSeek 兼容 OpenAI 格式，改个地址直接连上（不需要专门的包）
)
# 提示词模板：人格 + 历史占位符 + agent_scratchpad（Agent 中间思考过程的固定占位，固定写法背下来即可）
lc_prompt = ChatPromptTemplate.from_messages([
    ("system", PERSONA),
    MessagesPlaceholder("chat_history"),
    ("human", "{input}"),
    MessagesPlaceholder("agent_scratchpad"),
])
lc_agent = create_tool_calling_agent(lc_llm, [search_knowledge_base_lc], lc_prompt)
lc_executor = AgentExecutor(agent=lc_agent, tools=[search_knowledge_base_lc], verbose=True)  # verbose=True：思考过程打印在后端终端，对比手写版时重点看这个
```

**③ 在 `/api/chat` 函数体的最开头（`messages = req.messages` 之后）加 LangChain 分支**：

```python
    # ===== LangChain 分支（USE_LANGCHAIN = True 时接管：框架自动完成“决策-调用-回填”循环）=====
    if USE_LANGCHAIN:
        def generate():
            try:
                result = lc_executor.invoke({
                    "input": messages[-1]["content"],   # 最新一句话作为当前输入
                    "chat_history": messages[:-1],      # 其余作为历史（框架自动转成消息对象）
                })
                # 框架把多轮循环全部封装在 invoke 内部，一把返回最终文本（对照手写版的两次显式调用）
                yield f"event: token\ndata: {json.dumps({'content': result['output']}, ensure_ascii=False)}\n\n"
            except Exception:
                yield f"event: error\ndata: {json.dumps({'message': '模型服务暂时不可用，请稍后再试'}, ensure_ascii=False)}\n\n"
            yield "event: done\ndata: {}\n\n"

        return StreamingResponse(generate(), media_type="text/event-stream")
```

> 💡 对照着看，框架到底替你封装了什么：
>
> | 手写版要自己写的                | LangChain 版                     |
> | ----------------------- | ------------------------------- |
> | 几十行的工具描述 JSON           | `@tool` + docstring 自动生成        |
> | 解析 `tool_calls`、反序列化参数  | 框架自动                            |
> | 拼 assistant/tool 两条消息回填 | 框架自动（`agent_scratchpad` 占位符装这些） |
> | 自己控制两次调用                | `invoke` 一行，循环多轮也是它自动跑          |
>
> ⚠️ 代价也要亲眼看：**引用卡片没了**（框架不轻易把中间检索结果暴露给外层）、**打字机效果没了**（`invoke` 同步阻塞，一把返回）。要让卡片回来得用 `stream()`/callback 抓中间步骤，复杂度反而超过手写——**什么时候该手写、什么时候该用框架，答案就在这段体验里**，这是本步最值钱的面试素材。
>
> 日常开发保持 `USE_LANGCHAIN = False`（手写版能力更完整），只在对比测试时切 True。

### 10.7 前端：契约不变所以不用改；用新事件做等待状态播报（进阶）

**基础结论**：和第 5 步同样的架构红利——对外接口契约（POST /api/chat + SSE 流）没变，“模型内部决定查不查”是后端内部的事。新增的 `tool` 事件，前端解析器遇到不认识的事件名会自动跳过——**新增能力不破坏既有契约**，面试聊架构时又一次可以提。

**进阶（已实施）**：测 10.8 时会发现一个现象——闲聊时“思考中”的跳动点持续很久，查知识库时点一闪而过。原因：查库路径的第二次调用是流式的，首 token 秒到；闲聊路径全文一次性返回，等待期全在决策调用里。解法不是消灭等待，而是**让等待可见**：在 `sendMessage` 的事件循环里给 `tool` 事件加分支，模型决定查库时先把 AI 气泡写上状态提示（正文首 token 一到就被干净替换）：

```tsx
if (name === "tool") {
  // 第 7 步：模型决定查知识库时，先给用户一个明确的状态提示，替代干等（正文首 token 一到就被干净替换）
  if (payload.called) {
    patchLastMsg(convId, m => ({ ...m, content: "🔍 正在检索知识库…" }));
  }
} else if (name === "sources") {
```

小坑提醒：这句假内容不会被 `aiContent` 追加逻辑污染——`token` 分支是拿 `aiContent`（不含提示语）整体重写 `content`，首 token 一到即干净覆盖。这个改动本身就是“把工具决策过程可视化”的面试素材（商业产品的“正在搜索…”状态提示同款原理）。

### 10.9 注意事项 / 常见坑

| #  | 现象                                       | 原因与解决                                                                                                                                                                           |
| -- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1  | 模型该调时不调、不该调时乱调                           | 工具 `description` 措辞不到位。把“什么时候用/不用”写具体（对照 10.4 的写法），这是工具设计的核心活                                                                                                                   |
| 2  | 报错 400，提示 messages 格式不对                  | `role: "tool"` 的消息必须带 `tool_call_id` 且紧跟在含 tool_calls 的 assistant 消息之后，顺序和配对缺一不可                                                                                                |

### 10.10 面试知识点（这步的问答含金量最高，背熟）

**问：Function Calling（Tool Calling）是怎么实现的？**

请求时给模型传 tools 参数（工具名、描述、参数的 JSON Schema）；模型若决定调用，返回的不是文字而是结构化的调用意图（工具名 + 参数）；应用层解析后真正执行，把结果作为 tool 角色消息连同 assistant 的调用意图一起回填，再次请求，模型基于结果作答。**模型只决策不执行**，执行权始终在应用层。

**问：RAG 和 Agent 的区别？**

基础 RAG 是固定流水线：每次都先检索再生成，查不查由代码决定；Agent 是循环决策：模型根据任务自主选择、多次调用工具，能处理“检索 + 计算 + 多步骤”的复合任务。我的项目里两者都做过：第 5 步是流水线 RAG，第 7 步升级为 Tool Calling，检索决定权交给了模型，还保留了阈值过滤作第二道防线。

**问：为什么决策调用不流式？**

因为要先看到完整返回才能判断模型是“想调工具”还是“直接回答”。若它决定调工具，流式吐出来的文字反而要丢弃。所以架构是：决策阶段同步短调用，生成阶段才开流。

**问：为什么不直接用框架，要手写一遍？**

手写后才能说清框架封装了什么：工具描述生成、意图解析、结果回填、多轮循环。也才能判断框架的代价：抽象层深、中间结果不易拿（引用卡片难接）、报错堆栈长、版本激进。小项目手写更可控，复杂多 Agent 编排用框架更划算。

**问：模型乱调工具/不调工具怎么办？**

三层约束：① 工具描述把使用边界写具体（什么时候用、什么时候不用）；② 工具内部保留阈值过滤，不相关结果照样滤掉；③ 提示词人格兜底（不知道就说不知道）。本质是概率性行为，只能约束不能根除，工程上要有兜底方案。

**问：为什么不用 EventSource 而用 fetch 手写 SSE 解析？**（第 6 步旧题，可能连带问）

EventSource 只支持 GET，我们的对话要 POST 带历史。

```python
@app.get("/api/files/{filename}/download")
async def download_file(filename: str):
    """下载知识库原文件：原文件名 → 查 Chroma 元数据拿哈希名 → 返回磁盘实体文件"""
    data = collection.get(where={"filename": filename}, include=["metadatas"], limit=1)
    if not data["ids"]:
        raise HTTPException(status_code=404, detail="知识库中没有这个文件")
    saved_as = data["metadatas"][0].get("saved_as")
    if not saved_as:
        # 旧数据升级前入库，元数据里没有 saved_as——如实告知，不蒙混（第 6.5 步的错误提示原则）
        raise HTTPException(status_code=404, detail="该文件为历史入库数据，未记录原文件，请重新上传")
    file_path = os.path.join(UPLOAD_DIR, saved_as)
    if not os.path.exists(file_path):
        raise HTTPException(status_code=404, detail="服务器上的原文件已丢失，请重新上传")
    return FileResponse(file_path, filename=filename)  # filename 参数让浏览器按原文件名下载（中文名自动编码）
```

### 10.13 进阶优化：文件生命周期闭环（重复拒收 / 同名覆盖 / 物理清理）（已完成并实测）

**背景：三个真实撞上的问题**。日常使用中发现上传/删除有三个行为缺口：

1. 同一份文件重传，后端默默幂等覆盖，用户毫无感知（`duplicated` 标志算了但前端没接）；
2. 同名文件改了内容再传，旧版切片不清理——新旧两版在检索里同场竞争，“年假 5 天”和“年假 7 天”可能同时被捞进资料；
3. 删除文档只删 Chroma 切片，`uploads/` 里的物理文件成孤儿，磁盘悄悄积灰。

**设计核心：两条身份线管到底**。文件的身份由两个东西定义：内容指纹（MD5，决定存盘名和切片 ID）和原文件名（决定列表展示和删除范围）。三个补丁分别把两条线的交叉情况管完整：

```
传文件 → 内容指纹查库
   ├─ 内容已有（不管叫什么名）→ 409 拒收，告知已有文件名     【补丁①】
   ├─ 内容没有、同名旧版存在 → 清旧版（切片+物理文件）再入库  【补丁②】
   └─ 全新 → 直接入库
删除 → 切片 + 物理文件同步清，共享文件防误删               【补丁③】
```

**提示闭环（前端已接入）**：上传失败的 `!res.ok` 分支自动读后端 `detail` 弹窗（第 4 步铺好的路），409 的“禁止重复上传”提示直接送达用户；成功路径靠后端响应里的 `overwritten` 标志分流——新上传弹“上传成功：xxx（共 N 个切片）”，同名覆盖弹“同名文件覆盖成功：xxx（旧版已清理，新版共 N 个切片）”。三种结局三种声音，绝不静默。

#### 改动清单（后端三处 + 前端一处）

**① 公共地基：清理助手函数**（新增，放在 `delete_file` 接口上方）：

```python
def cleanup_saved_files(saved_names):
    """清理 uploads/ 里不再被引用的物理文件（覆盖/删除两条路共用）。
    防误删：同一份内容可能以不同文件名传过（指纹相同、共享一个存盘文件），
    必须等库里再没有任何切片引用这个 saved_as 时才删物理文件；
    os.remove 包 try 防 Windows 文件占用导致 500，清理失败不阻断主流程"""
    for name in saved_names:
        if not name:
            continue
        if len(collection.get(where={"saved_as": name})["ids"]) == 0:
            path = os.path.join(UPLOAD_DIR, name)
            if os.path.exists(path):
                try:
                    os.remove(path)
                except OSError as e:
                    print(f"[清理] 物理文件删除失败（不影响主流程）: {name} {e}")
```

两个细节是灵魂：**先删切片再查引用**（顺序反了永远删不掉）；**引用归零才删文件**（同内容不同名的两个版本共享存盘文件，删一个不能连坐另一个）。

| 删除受保护文件            | 403：“「公司制度.txt」是知识库的演示样本文件，不支持删除；需要更新内容时，上传同名文件即可自动覆盖旧版”；库内切片、uploads/ 物理文件均完好 ✅ |
| 删除不存在文件（回归）        | 仍是 404，不受禁删名单影响 ✅                                                                |
| 前端类型检查             | `npx tsc --noEmit` 零错误 ✅                                                         |
|                    |                                                                                  |
|                    |                                                                                  |

#### 已知边界（面试主动讲的料）

1. **“同名即同文档”假设**：两个不同部门各有一份“报告.txt”，后传的会覆盖先传的。学习项目可接受；生产系统用目录/命名空间区分同名文件。
2. **共享存盘文件的防误删**：同一内容以不同文件名传过两次（在 409 闸门之前历史上可能发生），两个版本共享一个物理文件——所以清理必须查引用归零，不能见名就删。
3. **409 顺手修了一个静默行为**：以前“同一内容换名字传”会默默把库里元数据的 filename 改成新名（卡片来源跟着变），现在被 409 拦下并明确告知，行为更诚实。

#### 面试说法

> “知识库文件管理我做了生命周期闭环：上传按内容指纹幂等，重复内容 409 拒收并告知已有文件名；同名不同内容视为新版本，先清旧版再入库，杜绝新旧两版在检索里同场竞争；删除时切片和物理文件同步清理，且防误删共享存盘文件——同一内容可能以不同文件名存在，必须引用归零才删实体。这里的设计原则是：**两条身份线（内容指纹、原文件名）交叉的每种情况都要有明确定义的行为**。”

### 11.1 痛点回顾：第 7 步留下了四个遗憾，这一步全部清算

💡 定位：**第 7 步学的是协议（意图→执行→回填），第 8 步学的是编排（把协议放进图里自动运转）。** 协议一字不变，编排全面升级。

### 11.2 概念回炉：三个核心 + 三代架构对照（预习验收）

**三个核心**（第 8 步预习讲过，这里固化）：

- **State（状态）**：随流程传递的共享便签——就是我们手写版的 `messages` 数组
- **Node（节点）**：一个工位——“调模型思考”是一个、“执行工具”是一个
- **Edge（边）**：工位间的路，条件边是岔路口——就是手写版那个 `if tool_calls:`

第 7 步的 Agent 循环，用图语言表达就是：

```
        ┌─────────┐   有调用意图   ┌─────────┐
入口 → │ 思考节点  │ ────────→ │ 工具节点  │
        └─────────┘ ←──────── └─────────┘
             │   结果回填，回去再想（自动循环）
             │ 没调用意图
             ↓
            出口
```

**三代架构演进表**（面试核心叙事线，背熟）：

| 维度   | 手写版                     | LangChain 版          | LangGraph 版（本步）          |
| ---- | ----------------------- | -------------------- | ------------------------ |
| 循环控制 | 固定两次调用                  | AgentExecutor 内部黑盒循环 | 显式图，自动循环带护栏              |
| 打字机  | ✅（仅调工具路径）               | ❌                    | ✅（全场景）                   |
| 并行调用 | 只取第一个                   | 框架自动                 | 框架自动                     |
| 防死循环 | 无                       | 有（默认）                | 有（recursion_limit 可调）    |
| 官方状态 | 自制                      | 遗留方案                 | 主推                       |
| 定位   | 日常主力→退役对照               | 对照标本                 | 新主力                      |
| 开关   | `USE_LANGCHAIN=False` 时 | `USE_LANGCHAIN=True` | `USE_LANGGRAPH=True`（默认） |

### 11.3 本步架构方案：一次讲清楚为什么这么设计（面试必背）

**① 用预构建 `create_react_agent`，不自己建图。** 原因：我们的场景是标准 ReAct 循环（思考⇄工具），预构建版本就是这张图的成品，一行建好；自己用 `StateGraph` 搭适合更复杂的多分支编排，现阶段是过度设计。但图的原理必须会讲（11.2），面试被问“你用过 StateGraph 吗”答“我们的场景用预构建更合适，自定义图适合 XX 场景”——**知道自己为什么不用，比用了更显水平**。  
**② 检索仍然由代码先做，再交给图生成回答。** 这是本步最重要的设计取舍，必须看懂：

- 如果让模型自己决定查不查（第 7 步模式），引用卡片只能等模型调完工具才能拿到——**卡片会从“回答之前”变成“回答之后”**，体验降级，还丢掉第 6.5 步的“未命中自然回应”能力（模型自己兜底的话术不可控）
- 而 RAG 应用的检索本来就该**无条件执行**（第 5 步的初心：问了就查，查到就答），“要不要查”的判断交给 1.1 阈值即可，不需要模型再决策一次——还省一次 API 调用
- 所以：**我们代码先检索拿卡片 → 发 `sources` 事件（卡片先出场，顺序不变）→ 把编号资料放进提示词交给 LangGraph 流式生成**。Agent 图负责的是“基于资料可靠地生成回答”，检索由确定性代码保证——**确定性的活给代码，生成性的活给模型**，这就是架构师的分工观。  
  **③ 多 Agent 分工为什么没做完整版？** 预习讲的“检索员+撰写员”两角色，本步用 `create_react_agent` + 检索提示词落地了核心分工思想（检索与生成职责分离）；完整的两节点 StateGraph 版列为进阶练习（11.12 会提），面试时口头能讲清分工价值即可。  
  **④ 三代同屏对照**：`USE_LANGGRAPH`（新主力）→ `USE_LANGCHAIN`（对照）→ 手写版（兜底），三个开关优先级依次判断，演进史全部保留在代码里。

```python
# ===== 第 8 步：LangGraph 版 Agent（新主力：流式输出 + 护栏齐全）=====
```

### 11.6 后端改造（二）：`/api/chat` 加 LangGraph 分支（流式 + 卡片）

定位 `chat()` 函数开头，**在 `if USE_LANGCHAIN:` 之前**插入（优先级：LangGraph → LangChain → 手写）：

```python
    # ===== LangGraph 分支（USE_LANGGRAPH = True 时接管，第 8 步新主力）=====
    if USE_LANGGRAPH:
        # 检索前先改写（已实测修复“那餐补呢”查不到的问题）：口语短句距离 1.478 过不了 1.1 阈值，
        # 改写成文档措辞后降到 0.398——第 7 步模型自主改写的能力在“代码先检索”架构里丢了，这里补回；
        # 带最近几轮历史解决多轮指代（“那它呢”），失败就用原话兜底，绝不阻断主流程（一次短调用的成本）
        try:
            rewrite = client.chat.completions.create(
                model="deepseek-v4-flash",
                messages=[{"role": "system", "content": "结合对话历史，把用户最新问题改写成一句独立完整的检索语句（贴近知识库文档措辞）。只输出检索语句本身，不要解释。若最新问题不是知识库查询类问题（闲聊、创作、讲故事等），原样输出该问题，不要改写、不要回答它。"}] + messages[-4:],
                # 末尾那句是 11.9 坑 10 事故的加固：闲聊/创作类请求没有对应检索语句，不给出口它可能自由发挥（直接编个故事）
            )
            rewritten = (rewrite.choices[0].message.content or "").strip()
        except Exception:
            rewritten = ""
        query = rewritten or messages[-1]["content"]
        print(f"[LangGraph 检索] 原话: {messages[-1]['content']} → 改写: {query}")  # 观察点：后端终端看改写效果
        hits = search_knowledge_base(query)  # 代码先检索：卡片先出场、未命中自然回应可控（设计取舍见 11.3）
        sources = []
        context_parts = []
        seen = set()
        for doc, meta in hits:  # 去重逻辑与手写版完全一致（第 6 步的活儿一行不丢）
            key = (meta.get("filename"), doc)
            if key in seen:
                continue
            seen.add(key)
            sources.append({"id": len(sources) + 1, "filename": meta.get("filename", "未知来源"), "snippet": doc})
            context_parts.append(f"[{len(sources)}] (来自: {meta.get('filename', '未知来源')})\n{doc}")
        material = "\n\n".join(context_parts) if context_parts else "（无）"

        async def generate():
            # 必须是 async def：里面有 async for（消费 LangGraph 异步流），普通 def 直接 SyntaxError（已实测踩坑，见 11.9 坑 9）；
            # StreamingResponse 对异步生成器原生支持，手写版的同步生成器不受影响
            yield f"event: sources\ndata: {json.dumps(sources, ensure_ascii=False)}\n\n"
            # 组装本次对话：人格+规则 + 历史 + 编号资料 + 当前问题（检索结果以资料形式进提示词）；
            # 【用户问题】必须用原话不能用改写句（query），否则闲聊请求会被改写模型篡改——事故与修复见 11.9 坑 10
            lg_messages = [{"role": "system", "content": GRAPH_SYSTEM}] + messages[:-1] + [
                {"role": "user", "content": f"【编号资料】\n{material}\n\n【用户问题】\n{messages[-1]['content']}"}
            ]
            try:
                # astream(stream_mode="messages")：模型每吐一个 token 就产出一条消息事件——全场景打字机的来源；
                # 对照第 7 步：手写版只有“调工具路径”才有打字机，这里闲聊也有（11.1 遗憾 1 清算）；
                # config 里的 recursion_limit=10 是防死循环护栏：最多转 10 圈强制熔断（新版 API 护栏在调用时传，不再在构图时传）
                async for _chunk, metadata in lg_graph.astream(
                        {"messages": lg_messages},
                        config={"recursion_limit": 10}, stream_mode="messages"):
                    if isinstance(_chunk, AIMessageChunk) and _chunk.content:
                        yield f"event: token\ndata: {json.dumps({'content': _chunk.content}, ensure_ascii=False)}\n\n"
            except Exception:
                yield f"event: error\ndata: {json.dumps({'message': '模型服务暂时不可用，请稍后再试'}, ensure_ascii=False)}\n\n"
            yield "event: done\ndata: {}\n\n"

        return StreamingResponse(generate(), media_type="text/event-stream")
```

**② 手写版分支保留不动**，只把原来的 `if USE_LANGCHAIN:` 改成 `elif USE_LANGCHAIN:`（因为前面多了 if）。改完整个判断链是：

```python
    if USE_LANGGRAPH:      # 新主力（默认开）
        ...
    elif USE_LANGCHAIN:    # 对照标本（日常关）
        ...
    # 手写版（兜底：两个开关都关时生效）
    ...
```

⚠️ 三个易错点：① `AIMessageChunk` 过滤必写——`stream_mode="messages"` 会产出工具消息、空内容块等，不过滤会把垃圾当正文发给前端；② `_chunk.content` 可能是 list 类型，这里用真值判断兼容两种；③ `elif` 别忘改，否则 LangGraph 跑完还会接着跑手写版。

### 11.7 前端：依然零改动（第三次验证架构红利）

第 5 步一次、第 7 步一次、这是第三次——**后端架构怎么换代，前端一行不动**。因为契约没变：还是 POST /api/chat，还是 sources/token/error/done 四个事件。唯一的变化是体验变好了：闲聊也有打字机（因为现在每个 token 都是流式来的）。`tool` 事件不再发送（LangGraph 分支不产生它），前端收不到就当没有，无副作用。

### 11.9 注意事项 / 常见坑（第 8 步专用）

### 11.10 面试知识点（这步的问答是编排能力的证明）

**Q1：为什么从 AgentExecutor 换到 LangGraph？**

> AgentExecutor 已被官方标记为遗留方案，循环逻辑是黑盒；LangGraph 把流程显式建成图，节点和边清晰可见，天然支持并行执行、护栏（recursion_limit）和细粒度流式。我们项目里三代实现都保留：手写版证明我懂协议，LangChain 版作对照，LangGraph 是当前主力。  
> **Q2：LangGraph 里的图是什么？你在页面上画图吗？**  
> 不是界面图形，是代码里的工作流结构：节点是步骤、边是流转规则、状态是随流程传递的共享上下文（我们的就是对话消息列表）。它的价值是编排显式化——循环走几圈、走哪条路一眼可见，还能加护栏和断点。  
> **Q3：打字机效果是怎么在 Agent 上实现的？**  
> Agent 运行有两类输出：步骤流（思考/工具）和最终生成的 token 流。产品上前者做状态提示，后者才进打字机。LangGraph 用 astream(stream_mode="messages") 拿逐 token 事件，过滤出模型的正文块转发给前端——第 7 步的 LangChain 版用 invoke 拿不到流，就是这个差别。  
> **Q4：你的检索为什么没交给 Agent 自主决策？**  
> 这是有意的取舍：自主决策会让引用卡片从“回答前”变“回答后”，体验降级；而且 RAG 的检索本来就该无条件执行，“是否相关”由相似度阈值判断即可。所以检索用确定性代码做，Agent 只负责基于资料生成回答——确定性的活给代码，生成性的活给模型，还省一次调用。  
> **Q5：多 Agent 一定要多个模型吗？**  
> 不一定。多 Agent 的本质是分工：同一个模型换角色设定、换职责范围就是不同 Agent。多模型混用是进一步的成本优化——简单环节用便宜模型，关键环节用强模型。我们是单模型多职责方案。  
> **Q6：怎么防止 Agent 无限循环烧钱？**  
> 两层：框架的 recursion_limit 强制熔断（我们设 10）；提示词里约束工具使用条件（资料已提供就不重查）。生产上还可以加单轮超时和费用告警。

### 12.2 概念回炉：MCP 三板斧（面试必背）

**① MCP 是什么**：Anthropic 2024 年底提出的开放协议，AI 界的 USB-C——工具方按标准打包成 Server，AI 方按标准做 Client，插上就能用，不用再一家家定制。

**② 三个角色**：

- **Server（供货方）**：把能力打包成标准服务。官方有几百个现成的（网页抓取、GitHub、数据库…），我们的知识库也将成为一个。
- **Client（消费方）**：按协议接入 Server 拿工具。我们的后端（经 `langchain-mcp-adapters` 适配）就是。
- **传输方式**：本章用 **stdio**（Client 把 Server 当子进程拉起，通过标准输入输出通信）——零网络配置，本地开发首选；生产跨机部署换 HTTP/SSE（12.12 进阶）。

**③ 和第 7 步协议的关系（关键认知）**：MCP 标准化的是**工具的供货侧**，模型消费工具的方式一点没变——MCP 工具经适配器转成 LangChain 工具后，生成的还是第 7 步那套 `name + description + parameters` 说明书，塞进 `tools` 参数。**模型根本不知道工具是本地函数还是 MCP 服务。**

### 12.3 本步架构方案（两个方向都做）

```
方向 A（当消费者）：牛来 → langchain-mcp-adapters → 官方 fetch MCP Server（子进程）
                     → 牛来获得联网抓取能力，知识库外的问题也能答了
方向 B（当供货商）：Claude Desktop / 任何 MCP 客户端 → stdio → 我们的知识库 MCP Server → Chroma
                     → 知识库从“页面内功能”升级为“生态可消费的标准服务”（作品集亮点）
```

四个设计决策（面试必背）：

1. **为什么方向 A 选 fetch**：官方参考实现、无需 API key、实用（实时网页内容正好补知识库的盲区）。
2. **USE_MCP 开关延续双版本对照传统**：False 时代码路径和第 8 步一字不差，方便对比；失败自动降级回普通图，绝不阻断。
3. **前端零改动**：MCP 工具在图内执行，走的是已有的 tool/token 事件管道；联网回答本就不该有知识库卡片，逻辑自洽。
4. **方向 B 为什么是亮点**：“我做过 MCP 客户端”和“我把自己的 RAG 做成了标准 MCP 服务”含金量天差地别——后者证明你懂协议、懂标准化、懂服务化。

```python
_mcp_tools_cache = None  # MCP 工具缓存：None=没加载过，[]=加载失败，有值=加载成功（三种状态别混，12.9 坑 2）

    """MCP 工具加载器（方向 A）：懒加载+缓存，stdio 子进程只拉起一次（12.9 坑 5）；
    失败给空列表降级，绝不阻断主流程（12.9 坑 2）"""
    global _mcp_client, _mcp_tools_cache
    if not USE_MCP:
        return []
    if _mcp_tools_cache is not None:
        return _mcp_tools_cache
    try:

                "command": sys.executable,       # 用当前 venv 的 python，别写死路径（12.9 坑 1）
```

```python
import sys

# 把 backend 根目录加入搜索路径：无论被 `python -m app.mcp_server` 还是被客户端用文件路径拉起，
# `from app.main import` 都成立（两种启动方式的 sys.path 不一样，12.9 坑 4）
sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))

from mcp.server.fastmcp import FastMCP
from app.main import search_knowledge_base as rag_search  # 复用同一个执行体：检索能力只有一份；起别名避免和下面的工具函数同名（12.9 坑 7）

mcp = FastMCP("ai-workspace-knowledge")  # 服务名：客户端里会看到这个名字


@mcp.tool()
def search_knowledge_base(query: str) -> str:
    """检索企业知识库（用户上传的文档）。传入检索语句，返回最相关的文档片段及来源文件名。
    当问题涉及公司制度、内部规定、工作事务或员工个人档案时使用。"""
    hits = rag_search(query)
    if not hits:
        return "知识库中没有检索到相关内容"
    parts = [f"[{i + 1}] (来自: {meta.get('filename', '未知来源')})\n{doc}" for i, (doc, meta) in enumerate(hits)]
    return "\n\n".join(parts)


if __name__ == "__main__":
    mcp.run(transport="stdio")  # stdio：靠标准输入输出通信，由客户端当子进程拉起；不监听任何端口（12.12 进阶换 HTTP）
```

- **docstring 就是给外部客户端的模型看的说明书**（同 12.2 ③：协议只换供货侧，消费侧照旧）。
- 代价：`from app.main import` 会连带执行 main.py 的模块级初始化（Chroma、构图），启动稍慢——未来抽取到 `services/` 可解（12.9 坑 8）。

### 12.10 面试知识点（MCP 是 2025 后的热点，这段必背）

> **Q1：MCP 和 Function Calling 什么关系？**  
> 一个管消费一个管供货：Function Calling 是模型消费工具的协议（tool_calls + JSON Schema）；MCP 是工具供给侧的标准化——工具打包成 Server，任何 Client 即插即用。MCP 工具进入我的系统后，最终还是变成 Function Calling 的说明书塞进 tools 参数——模型无感知。
>
> **Q2：你的项目怎么接的 MCP？**  
> 双向：作为客户端，经 `langchain-mcp-adapters` 把官方 fetch Server 的工具转成 LangChain 工具，和本地工具同列表进 LangGraph 图，配 USE_MCP 开关和失败降级；作为服务端，用 FastMCP 把知识库检索暴露为标准服务，Claude Desktop 等客户端直接消费——知识库从页面功能升级成了生态服务。
>
> **Q3：stdio 和 HTTP 传输怎么选？**  
> stdio 零配置、本地首选，但服务和客户端同机同生命周期；跨机部署、多客户端共享一个服务换 Streamable HTTP。我先 stdio 跑通协议理解，HTTP 是进阶项。
>
> **Q4：接第三方 MCP 工具有什么风险？**  
> 三个：权限（工具能干什么要审）、提示注入（恶意工具描述可能诱导模型，工具毒化攻击）、稳定性（外部依赖要超时和降级）。我的实践：只接官方参考实现 + 失败降级不阻断 + 提示词约束调用场景。
>
> **Q5：为什么不把本地工具都改成 MCP？**  
> 没必要：同进程工具直接注册成本最低；MCP 的价值在跨进程/跨应用的标准化共享。我的知识库需要被外部客户端消费才包装成 Server，fetch 需要跨进程提供才走 Client——形式跟着需求走。
>
> **Q6：MCP 工具和本地工具在模型眼里有区别吗？**  
> 没有。都是 name+description+parameters 三件套。区别在模型看不见的地方：执行时一个调本地函数，一个经 JSON-RPC 发给子进程/远程服务。

#### 改动 ①：`get_mcp_tools()` 升级成多 Server 版（约第 132-142 行）

把原来 try 块里的配置和加载段整体换成下面这版，**三处变化：配置加 weather 条目、双会话嵌套打开、新增工具精简过滤**：

```python
    try:
        _mcp_client = MultiServerMCPClient({
            "fetch": {
                "command": sys.executable,       # 用当前 venv 的 python，别写死路径（12.9 坑 1）
                "args": ["-m", "mcp_server_fetch"],
                "transport": "stdio",
            },
            "weather": {                          # 12.13 新增：Open-Meteo 天气 Server（免费、免 key）
                "command": sys.executable,
                "args": ["-m", "open_meteo_mcp"],
                "transport": "stdio",
            }
        })
        # 几个 Server 就要开几个会话（嵌套 with），开后 get_tools() 才能拿全（实测合计 9 个工具）
        async with _mcp_client.session("fetch"):
            async with _mcp_client.session("weather"):
                all_tools = await _mcp_client.get_tools()
        # 工具精简（12.13 核心设计点）：天气 Server 自带 8 个工具，
        # 时区转换/空气质量类与模型自身能力重叠、徒增决策噪音，只留天气相关的 4 个 + fetch 本体（过滤后共 5 个）
        _mcp_tools_cache = [
            t for t in all_tools
            if t.name == "fetch" or t.name in {
                "get_current_weather",            # 当前天气：“北京现在天气怎么样”
                "get_weather_byDateTimeRange",    # 日期范围预报：“明天天气怎么样”
                "get_weather_details",            # 详细天气（含预报）：“给我份详细天气报告”
                "get_current_datetime",           # 当前时间：模型算“明天”是哪天要靠它（所以没被精简掉）
            }
        ]
        print(f"[MCP] 已加载工具: {[t.name for t in _mcp_tools_cache]}")
```

（except 块和函数其余部分保持原样，不用动。）

> **为什么要精简（面试重点）**：回忆 12.2 说的“工具不是免费的”。天气 Server 一口气带了 8 个工具，全注册的代价：① 说明书翻倍，每轮对话输入费上涨；② 时区转换和模型自身能力重叠，误调率上升；③ 工具越多，调教说明书的负担越重。原则：**只注册与业务场景匹配的工具，白送的也不要。**

#### 新增坑（接在 12.9 之后）

1. **工具别全注册**：天气 Server 暴露 8 个工具，照单全收会让说明书成本翻倍、决策噪音变大——按名字过滤，只留业务需要的（本节改动 ①）
2. **多 Server 要开会话**：几个 Server 就要嵌套开几个 `session()`，`get_tools()` 才能拿全；只开一个就只能拿到一个 Server 的工具（本节改动 ①）

**为什么后端不能上 Serverless**（这条淘汰了 Vercel / Render 那一类，面试可讲）：

| 现有代码                                                          | 与 Serverless 的冲突点                                         |
| ------------------------------------------------------------- | --------------------------------------------------------- |
| `agents.py` 中 MCP 用 `sys.executable -m mcp_server_fetch` 拉子进程 | 不允许 spawn 常驻子进程；请求结束进程即被杀，MCP 会话直接断                       |
| `config.py` 中 Chroma 用 `PersistentClient(path=...)` 读写本地磁盘    | Serverless 磁盘临时且只读，写完就没                                   |
| `main.py` 用 `StreamingResponse` 做 SSE 流式输出                    | 有执行时长上限（Serverless 的通用限制，Vercel 免费档默认在十秒量级），牛来说一段长回答可能被掐断 |

**关键区分**：创空间虽然也是「平台托管」，但它是**长驻容器**（K8s Pod + supervisord），**不是 Serverless 函数**——上面三条冲突一个都不存在：磁盘实测可写、进程实测是 root 常驻、SSE 没有函数式超时。**所以「不能上 Serverless」这条结论不构成对创空间的否定。**

#### 13.3.1 架构决策：一个容器、一个端口、前后端同源

**为什么必须这么定**：探针实测到平台**只放一个端口出来**（UI 明写「Docker模式端口固定为7860」，容器内 `LISTENING_PORT=7860`）。牛来现在是两个服务两个端口（前端 3000、后端 8000），直接搬上去必死。

**方案**：把 Next.js **静态导出**成一堆纯 HTML/JS/CSS，交给 FastAPI 一起托管。最终**一个容器、一个进程、一个端口 7860**。

```
面试官浏览器
     ↓ https
魔搭网关（PAI-EAS，张家口机房）
     ↓ 转发到容器 7860
FastAPI（唯一进程）
     ├── /api/chat                  → 对话（SSE 流式）
     ├── /api/upload                → 上传
     ├── /api/files                 → 清单
     ├── /api/files/{name}          → 删除
     ├── /api/files/{name}/download → 下载
     ├── /health                    → 健康检查
     └── /                          → 前端静态文件（index.html + _next/）
```

**三个收益**：

1. **CORS 问题彻底消失**——前端页面和 API 同一个 origin，浏览器根本不触发跳域检查
2. **不用装 nginx**——省一个组件、省一份配置，2vCPU 上也少占资源
3. **面试官只需要记一个网址**

**可行性依据（已实测）**：前端 11 个源文件里，**0 个 API Routes（无 `route.ts`）、0 处 `next/image`、0 处 SSR 专属 API**，`page.tsx` / `ChatInput.tsx` / `MessageList.tsx` / `Sidebar.tsx` / `Welcome.tsx` 五个文件第一行全是 `"use client"`。**这是一个纯客户端应用，本来就没用到 Next.js 的服务端能力。**

**但这条路线（下称方案 B）目前只是「根据实测推导出的假设」，`next build` 还没真跑过。** 13.3.3 第 1 步的实测结果出来后才算定案。如果失败，备选是：

**方案 C：Next.js 当唯一的服务器**（`output: 'standalone'` 跑 Node），Python 作为同容器内的子进程跑在 8000，Next 用 `rewrites()` 把 `/api/*` 反代过去。

| 对比           | 方案 B 静态导出                                       | 方案 C Next standalone + Python 子进程                                                                    |
| ------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 容器内进程数       | **1 个**（Python）                                 | 2 个（Node + Python）                                                                                   |
| 镜像           | 只装 Python                                       | Node + Python 两套运行时，大很多                                                                              |
| 保留 SSR       | ❌                                               | ✅（但本项目 0 处用到，见 13.0.1 表 A 补充）                                                                        |
| 同源 / CORS 消失 | ✅                                               | ✅（`rewrites` 是服务端代理，浏览器仍看到单一 origin）                                                                 |
| SSE 打字机      | ✅ FastAPI 直出                                    | 🔶 多一跳 Node 代理，有被缓冲的风险                                                                               |
| 启动方式         | `CMD` 一句话                                       | 要写 shell 脚本拉两个进程；**平台那份 supervisord 配置能不能改未验证**（探针只看到 `SUPERVISOR_SOCK_PATH=/etc/supervisor/conf-*`） |
| 失败模式         | 少                                               | 多（Node 挂了 / Python 挂了 / 谁重启谁）                                                                        |
| 产物自由度        | **纯静态文件，将来换 Vercel / EdgeOne / 自己 nginx 都能直接用** | 绑定 Node 运行时                                                                                          |

**两案的前端改造是共用的**：13.3.4 抽 `API_BASE` 在 B、C 下做法完全一样（同源 → 生产环境给空串）。所以**先做 13.3.3、13.3.4 不会白做**，等实测结果再定走哪条。

**本地不配 `DATA_DIR`，行为与改前完全一致**（默认值就是原来那个路径），所以这一改不会影响现有开发。

#### 13.3.9 种子文档脚本：解决「部署完知识库是空的」

**问题**：根 `.gitignore` 第 8、9 行排除了 `uploads/` 和 `chroma_db/`。代码推上创空间后知识库一个切片都没有，连禁删的演示样本「公司制度.txt」也不在（它的原名只活在 Chroma 元数据里，磁盘上叫 `73499e7baf7bc6d1b7829f6031df0bcc.txt`）。

**后果**：面试官打开页面问「年假有几天」，牛来回答「知识库里没有相关资料」。**演示当场翻车。**

**解法**：写一个幂等的种子脚本，容器启动时自动跑一遍。

**新建 `backend/seed.py`**：

```python
"""知识库种子文档灌入脚本（部署专用，本地开发不需要跑）。

为什么需要它：.gitignore 排除了 uploads/ 和 chroma_db/，代码推上创空间后知识库是全空的，
连禁删的演示样本「公司制度.txt」都没有，面试官一问 RAG 就会得到“知识库里没有相关资料”。
所以容器每次启动都跑一遍这个脚本，把演示文档灌回去。

幂等性（跑多少遍结果都一样）靠下面“按文件名查，已存在就整个跳过”保证。
为什么不按内容指纹查：本地那份文件实测是 CRLF 分隔、无末尾换行（MD5 = 73499e7b...），
而本文件里的字符串常量用的是 \n，两者字节不同 → 指纹也不同。
按指纹查会在本地多灌一份同名不同内容的副本，检索时两份相似内容一起被捞出来，
前端会出现重复的引用卡片。按文件名查就没这个问题。
"""
import os

from app.config import UPLOAD_DIR, collection
from app.rag import split_text

# 演示文档：文件名 → 正文。
# 这三行就是当前本地 uploads/ 里那份 195 字节样本的完整内容（已逐字核对）。
# 「公司代号 89757」那条是故意放的：用来演示“模型不会把内部信息说出去”的人格约束。
SEED_DOCS = {
    "公司制度.txt": (
        "公司休假制度：入职满一年享 5 天年假，满五年享 10 天。\n"
        "加班餐补：工作日加班晚于 19 点，每餐补贴 30 元。\n"
        "公司代号：89757，对外一律不使用。\n"
    ),
}


def seed():
    """把所有种子文档灌进知识库。已存在的整个跳过，不存在的补上。"""
    os.makedirs(UPLOAD_DIR, exist_ok=True)
    for filename, text in SEED_DOCS.items():
        # 按【文件名】查而不是按内容指纹查，理由见文件头注释
        if collection.get(where={"filename": filename})["ids"]:
            print(f"[种子] {filename} 已在库中，跳过")
            continue

        chunks = split_text(text)
        if not chunks:
            print(f"[种子] {filename} 切不出片，跳过")
            continue

        # 磁盘存原文件 + 算内容指纹，命名规则和 main.py 的上传接口保持一致：
        # 存盘名 = 内容 MD5 + 原后缀。两边规则一致，下载接口才能正常拿到原文件。
        import hashlib
        content = text.encode("utf-8")
        content_hash = hashlib.md5(content).hexdigest()
        ext = os.path.splitext(filename)[1].lower()
        save_name = f"{content_hash}{ext}"
        with open(os.path.join(UPLOAD_DIR, save_name), "wb") as f:
            f.write(content)

        ids = [f"{content_hash}-{i}" for i in range(len(chunks))]
        collection.upsert(
            documents=chunks,
            ids=ids,
            metadatas=[{"filename": filename, "saved_as": save_name}] * len(chunks),
        )
        print(f"[种子] {filename} 已灌入 {len(chunks)} 个切片")

    print(f"[种子] 完成，知识库当前切片总数: {collection.count()}")


if __name__ == "__main__":
    seed()
```

**注意 import 路径**：脚本里写的是 `from app.config import ...`，所以**必须在 `backend/` 目录下运行**，和 `test_mcp_kb.py` 的约定一样。

**本地验证（幂等性测试）**：

```powershell
cd e:\ai-workspace\backend
.\venv\Scripts\python.exe seed.py
.\venv\Scripts\python.exe seed.py
```

**连跑两遍，两遍都应该输出「`公司制度.txt` 已在库中，跳过」**，且最后一行的切片总数两次相同。

为什么本地也是「跳过」：因为你本地库里已经有这个文件名了（就是那份 195 字节的样本）。**这正是我们想要的结果——本地跑这个脚本零副作用。** 线上是空库，所以会真的灌入。

#### 13.3.10 `requirements.txt` 修复（两个问题一次解决）

**两个问题**：

1. 第 97 行 `pywin32==312` 没有 environment marker → **Linux 上 `pip install` 直接失败**（Windows 专属包，无 manylinux wheel）
2. 整个文件是 **UTF-16 LE with BOM** → git 判定为二进制，`git diff` 看不到依赖变更，**GitHub 网页显示「Binary file not shown」**

**根因**（记下来别再犯）：PowerShell 5.1 的 `>` 重定向默认输出 UTF-16 LE with BOM，所以 `pip freeze > requirements.txt` 每次都在制造二进制文件；而 `pip freeze` 会丢掉 `mcp` 声明的 `pywin32>=310; sys_platform == 'win32'` 里的 marker，让它变成无条件顶级依赖。

**修法 A：在 PyCharm 里改（推荐，零脚本风险）**

底部状态栏点当前的编码名（会显示 `UTF-16LE`）→ 在弹出菜单里选 **`UTF-8`** → PyCharm 会弹窗问你 **Reload** 还是 **Convert**：

| 选项              | 行为                          | 选它的后果                           |
| --------------- | --------------------------- | ------------------------------- |
| **Convert（转换）** | 把内容用新编码**重新写回磁盘**           | ✅ **要选这个**                      |
| Reload（重新加载）    | 用新编码**重新解释磁盘上原有的字节**，文件内容不变 | ❌ 会用 UTF-8 去解 UTF-16 的字节 → 满屏乱码 |

菜单里那个 **「移除 BOM」** 按钮不用点——它是给「已经是 UTF-8 但带 BOM」的文件用的。你现在是 UTF-16LE，直接转 UTF-8 即可；PyCharm 写 UTF-8 默认**不带 BOM**（`Settings → Editor → File Encodings → Create UTF-8 files` 默认值是 `with NO BOM`）。

转完再改 `pywin32` 那一行：`Ctrl+F` 搜 `pywin32`，把

```
pywin32==312
```

改成

```
pywin32==312; sys_platform == "win32"
```

`Ctrl+S` 保存。**两个问题一次解决，全程不用碰 PowerShell。**

> 💡 **PyCharm 转换时会顺手把行尾从 CRLF 改成 LF**，所以字节数会和修法 B 不一样，**两个都对**：
>
> | 修法                                                       | 行尾   | 实测字节数    |
> | -------------------------------------------------------- | ---- | -------- |
> | A（PyCharm）                                               | LF   | **2573** |
> | B（PowerShell 脚本，`WriteAllLines` 用 `Environment.NewLine`） | CRLF | **2705** |
>
> 差的 132 字节正好是 132 行各少一个 `\r`。Docker 里跑的是 Linux，**LF 反而更干净**，pip 两种都能正常解析。

**改完的效果（已用 `packaging.requirements.Requirement` 实测）**：全文件 132 行逐行解析 **0 失败**；第 97 行拆出 `name=pywin32` / `specifier===312` / `marker=sys_platform == "win32"`，在 **Linux 上求值为 `False`（跳过安装）**、在 **Windows 上求值为 `True`（正常安装）**；且全文件**只有第 97 行**带 marker，说明没误改其他行。

**修法 B：用 PowerShell 脚本**（没有 IDE 时用；先探测编码 → 再读取改行 → 以 UTF-8 无 BOM 写回）：

> 🔴 **下面每一行都是独立完整的语句，整块粘贴可以，一行一行敲也可以。不要把它改回跳行的 `if / elseif / else` 链。**
>
> **坑一（不幂等，2026-09-03 实测）**：最早的版本没有守卫，无条件按 UTF-16 读。第一次跑是成功的，**第二次跑就把文件毁了**——把已经是 UTF-8 的字节流当成 UTF-16LE 解码，每两个 ASCII 字节合成一个汉字，132 行塌成 1 行，2680 字节膨胀成 4058 字节的 `楡桯灡祰祥扥污獬…` 乱码，最后靠 `git checkout` 才恢复。
>
> **坑二（逐行粘贴会断，2026-09-03 实测）**：第二版用了跳行的 `if / elseif / else`。在 PowerShell 5.1 控制台里逐行粘贴时，单行写全的 `if (...) { ... }` 一敲回车就立即执行完了，下一行的 `elseif` 就成了孤立命令，报「无法将 elseif 项识别为 cmdlet」。所以下面故意拆成 **4 个各自独立的单行 `if`**。
>
> 现已用 PowerShell 官方 Parser 逐行验证：**12 行全部能独立解析**；并在副本上**连跑三遍**：第 1 遍转换，第 2、3 遍识别出已修好并完全不碰文件。

```powershell
cd e:\ai-workspace\backend
$p = (Resolve-Path "requirements.txt").Path
$b = [System.IO.File]::ReadAllBytes($p)

# ★ 守卫：先看清现在到底是什么编码，再决定怎么读。
#   绝不能无条件按 UTF-16 读——那样第二次跑就会把已经修好的文件毁掉。
#   下面 4 行是 4 个各自独立的 if，故意不写成 if/elseif 链，就是为了逐行粘贴也不会断。
$enc = "OK"
if ($b[0] -eq 0xFF -and $b[1] -eq 0xFE) { $enc = "Unicode" }
if ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF) { $enc = "UTF8" }
if ($enc -eq "OK" -and ($b | Where-Object { $_ -eq 0 }).Count -gt 0) { $enc = "BROKEN" }
"① 探测结果：$enc"

# 只有 Unicode / UTF8 两种情况才真的读取并改 pywin32 那一行；OK 和 BROKEN 都不动文件
if ($enc -eq "Unicode" -or $enc -eq "UTF8") { $lines = Get-Content $p -Encoding $enc | ForEach-Object { if ($_ -match '^pywin32==') { 'pywin32==312; sys_platform == "win32"' } else { $_ } } } else { $lines = $null }
# 关键：UTF8Encoding($false) 才是「无 BOM」。PowerShell 5.1 的 -Encoding UTF8 会带 BOM，不能用
if ($lines) { [System.IO.File]::WriteAllLines($p, $lines, (New-Object System.Text.UTF8Encoding $false)) }
if ($lines) { "② 已写回 $($lines.Count) 行，UTF-8 无 BOM" } else { "② 未写回（$enc）" }
```

**`$enc` 的四种取值**：

| 值         | 含义                               | 会动文件吗                                                |
| --------- | -------------------------------- | ---------------------------------------------------- |
| `Unicode` | UTF-16 LE with BOM，**你现在就是这个状态** | ✅ 转换                                                 |
| `UTF8`    | UTF-8 但带 BOM                     | ✅ 只脱 BOM                                             |
| `OK`      | 已经是 UTF-8 无 BOM，这一步早做完了          | ❌ 不碰                                                 |
| `BROKEN`  | 没有 BOM 却含空字节 = 已被错误转换过           | ❌ 不碰，先 `git checkout -- backend/requirements.txt` 恢复 |

**首次执行应该输出这两行**（实测值）：

```
① 探测结果：Unicode
② 已写回 132 行，UTF-8 无 BOM
```

**再粘一遍会变成**（这就是幂等，重复跑不会毁文件）：

```
① 探测结果：OK
② 未写回（OK）
```

**🔴 PowerShell 5.1 编码专题（本项目已踩五次，务必记住）**

Windows 自带的 PowerShell 5.1 对**无 BOM 的 UTF-8 文件**默认按系统 ANSI 代码页（中文系统是 GBK）解码，后果分两种：

| 命令                                    | 实测行为                                                            | 结论                                                                                                      |
| ------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `Get-Content 文件`（不带 `-Encoding`）      | 3919 行的本手册被读成 **3215 行**；`-match "牛来"` 返回 **False**（而内容明明就在文件里） | ❌ **不可信**，必须写成 `Get-Content 文件 -Encoding UTF8`                                                          |
| `Select-String -Path 文件 -Pattern ...` | 找中文、找英文都返回 **True**                                             | ✅ **它自己会探测 UTF-8**，可以放心用（第 13.3.3 / 13.3.4 的验证命令就是靠这条）                                                  |
| `命令 > 文件.txt`（重定向）                    | 输出成 **UTF-16 LE with BOM**                                      | ❌ 这就是 `requirements.txt` 变成二进制文件的根因（见 13.3.10）                                                          |
| `Out-File -Encoding UTF8`             | PS 5.1 的 `UTF8` 是**带 BOM** 的                                    | ❌ 要无 BOM 得用 `[System.IO.File]::WriteAllLines($p, $lines, (New-Object System.Text.UTF8Encoding $false))` |

**为什么行数会变少**：GBK 是双字节编码，前导字节（0x81~0xFE）会把紧跟的下一个字节一起吃掉，**连换行符 `0x0A` 也吃**，于是若干行被合并了。

**一句话记法**：**读文件用 `Select-String` 或 `Get-Content -Encoding UTF8`，写文件用 .NET 的 `UTF8Encoding($false)`，永远不要用 `>` 重定向存文本。**

**🔴 PowerShell 5.1 控制台粘贴专题（2026-09-03 做 13.3.10 时实测踩到）**

| 现象                                                                                   | 原因                                                                                      | 对策                                                                                                    |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 逐行粘贴多行 `if / elseif / else`，第一行正常执行，后面几行报「无法将 `elseif` 项识别为 cmdlet、函数、脚本文件或可运行程序的名称」 | 单行写全的 `if (...) { ... }` 是**语法完整的语句**，一敲回车控制台就立即执行了；等到下一行时 `elseif` 已经脱离原来的 `if`，成了孤立命令 | 要么**整块一次性粘贴**，要么把逻辑拆成**多个各自独立的单行 `if`**（本手册 13.3.10 就是这么改的，已用 PowerShell 官方 Parser 逐行验证过 12 行全部能独立解析） |
| 粘完多行块后停在 `>>` 提示符不动，代码根本没执行                                                          | 控制台的**多行输入必须再敲一个空行回车才提交**，光打上最后的 `}` 不算结束                                               | 在 `>>` 下**直接按一次 Enter**（空行）把它提交；想放弃就按 `Ctrl+C`                                                        |

**怎么分辨自己是不是卡在 `>>`**：看提示符。`PS E:\...>` 是正常态，`>>` 就是还有未提交的多行输入。不确定时先按 `Ctrl+C` 退回正常态最保险。

**另外三个同源陷阱（2026-09-03 做 13.3.10 时实测踩到）**

| 陷阱                                            | 现象                                                                                                                      | 对策                                                                                                                             |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **`.NET` 静态方法不认 PowerShell 的 `cd`**           | `[System.IO.File]::ReadAllBytes("requirements.txt")` 报「未能找到文件 `C:\Users\<你>\requirements.txt`」——明明已经 `cd` 到 `backend` 了 | .NET 的 `Environment.CurrentDirectory` 是**进程启动目录**，不跟着 PowerShell 的 `Location` 变。必须先 `$p = (Resolve-Path "文件").Path` 转成绝对路径再传进去 |
| **编码转换命令不幂等，重跑就毁文件**                          | `Get-Content -Encoding Unicode` 跑第二遍，把已经是 UTF-8 的文件当 UTF-16LE 解，132 行塌成 1 行、2680 字节膨胀成 4058 字节乱码                        | 转换前**先读 BOM 判断当前编码**，已经是目标编码就直接跳过（13.3.10 的守卫写法）。已毁的可靠 `git checkout -- <文件>` 从 HEAD 恢复                                        |
| **`git diff --numstat` 对「二进制→文本」永远显示 `-  -`** | UTF-16 转成 UTF-8 之后 `git diff --numstat` 仍然输出两个横杠，看起来像修失败了                                                               | git 是**按 blob 逐个**判二进制的，只要**旧版本**含 NUL 字节，这一对 diff 就整体算二进制。这是正常现象，**提交之后**再改才会显示具体数字                                           |
