**打开 PowerShell**（Win 键 → 输入 powershell → 回车），依次输入以下命令检查：

### 4.4 初始化后端（在 PyCharm 的 Terminal 里执行）

**① 创建虚拟环境（重点理解这个）**

```powershell
python -m venv venv
```

> 💡 这句是什么意思？
>
> **虚拟环境** = 给这个项目单独建一个“包仓库”。这样这个项目装的包不会和别的项目冲突（类似前端每个项目有自己的 node_modules，而不是全局装）。
>
> 执行后 backend 目录下会多出一个 `venv` 文件夹，里面是这个项目专用的 Python 和包。
>
> 命令执行完没有任何输出是正常的，等 10-30 秒。

**② 激活虚拟环境**

```powershell
.\venv\Scripts\Activate.ps1
```

- 注意开头是 `点+反斜杠`：`.\`，PowerShell 里执行当前目录脚本必须这么写。
- 激活成功的标志：命令行开头出现 `(venv)` 前缀，例如：
  ```
  (venv) PS D:\ai-workspace\backend>
  ```
- **如果报错“禁止运行脚本/execution policy”**（Windows 安全策略拦截，很常见），先执行这一句再重试：
  ```powershell
  Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
  ```
  中间弹出询问输入 `Y` 回车。这个只需执行一次，以后永久生效。
- 以后每次新开终端写后端代码前，都要先执行这句激活。不想干了就执行 `deactivate` 退出。

**③ 安装后端依赖**

```powershell
pip install fastapi uvicorn openai python-dotenv
```

> 💡 每个包是干什么的：
>
> - `fastapi`：Web 框架，写接口用的（类似前端的 Express）
> - `uvicorn`：服务器，负责把 FastAPI 跑起来（类似 node xxx.js 启动服务）
> - `openai`：调用大模型 API 的 SDK（DeepSeek 兼容 OpenAI 格式，所以用它）
> - `python-dotenv`：读 .env 配置文件用的（存 API Key）
>
> `pip` 是 Python 的包管理器 = 前端的 npm/pnpm。
>
> 如果下载慢，换清华镜像：
>
> ```powershell
> pip install fastapi uvicorn openai python-dotenv -i https://pypi.tuna.tsinghua.edu.cn/simple
> ```

## 五、第二步：最小功能（流式对话）

### 5.1 后端 `backend/app/main.py`

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import StreamingResponse
from openai import OpenAI
import os
from dotenv import load_dotenv

load_dotenv()

app = FastAPI(title="AI Workspace")

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_methods=["*"],
    allow_headers=["*"],
)

client = OpenAI(
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com"
)

@app.post("/api/chat")
async def chat(message: str):
    """流式对话接口"""
    def generate():
        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=[{"role": "user", "content": message}],
            stream=True
        )
        for chunk in response:
            if chunk.choices[0].delta.content:
                yield chunk.choices[0].delta.content

    return StreamingResponse(generate(), media_type="text/plain")
```

### 5.4 前端 `frontend/src/app/page.tsx`

用 VSCode 打开 frontend 项目，在左侧找到 `src/app/page.tsx`，把里面的内容**全部删掉**，换成下面的代码：

```tsx
"use client";
import { useState } from "react";

export default function Home() {
  const [input, setInput] = useState("");
  const [messages, setMessages] = useState<{role: string, content: string}[]>([]);
  const [loading, setLoading] = useState(false);

  const sendMessage = async () => {
    if (!input.trim()) return;

    const userMsg = { role: "user", content: input };
    setMessages(prev => [...prev, userMsg]);
    setInput("");
    setLoading(true);

    const response = await fetch(
      "http://localhost:8000/api/chat?message=" + encodeURIComponent(input),
      { method: "POST" }
    );

    const reader = response.body?.getReader();
    const decoder = new TextDecoder();
    let aiContent = "";

    setMessages(prev => [...prev, { role: "assistant", content: "" }]);

    while (reader) {
      const { done, value } = await reader.read();
      if (done) break;
      aiContent += decoder.decode(value);
      setMessages(prev => {
        const newMsgs = [...prev];
        newMsgs[newMsgs.length - 1] = { role: "assistant", content: aiContent };
        return newMsgs;
      });
    }
    setLoading(false);
  };

  return (
    <div className="max-w-2xl mx-auto p-4">
      <h1 className="text-2xl font-bold mb-4">AI Workspace</h1>

      <div className="space-y-4 mb-4 min-h-[400px] border rounded p-4">
        {messages.map((msg, i) => (
          <div key={i} className={msg.role === "user" ? "text-right" : "text-left"}>
            <div className={`inline-block p-3 rounded-lg ${
              msg.role === "user" ? "bg-blue-500 text-white" : "bg-gray-100"
            }`}>
              {msg.content}
            </div>
          </div>
        ))}
        {loading && <div className="text-gray-400">AI 正在思考...</div>}
      </div>

      <div className="flex gap-2">
        <input
          value={input}
          onChange={(e) => setInput(e.target.value)}
          onKeyDown={(e) => e.key === "Enter" && sendMessage()}
          placeholder="输入消息..."
          className="flex-1 border rounded px-4 py-2"
        />
        <button
          onClick={sendMessage}
          disabled={loading}
          className="bg-blue-500 text-white px-6 py-2 rounded hover:bg-blue-600 disabled:opacity-50"
        >
          发送
        </button>
      </div>
    </div>
  );
}
```

## 六、第 3 步：多轮对话记忆

> 本步目标：让 AI “记住”前面说过的话——你告诉它“我叫赵亮”，再问“我叫什么”，它能答上来。
>
> 预计耗时：30 分钟。只改 2 个文件：后端 `main.py` + 前端 `page.tsx`。

### 6.1 先看现在的问题（花 30 秒体验一下）

用现在的程序做个测试：

1. 问：“我叫赵亮，请记住”
2. 再问：“我叫什么名字？”
3. AI 答不上来 ❌

这不是 bug，是大模型的特性：**模型本身没有记忆**，每次 API 调用都是独立的，它只能看到你这一次发过去的那一句话。

### 6.2 解决思路（行业标准做法）

记忆不靠模型，靠我们自己的程序：**前端把整份聊天记录一起发给后端，后端原样转给大模型**。模型每次都能看到完整的历史，自然就能“接上话”了。

```
第1轮：[用户:我叫赵亮]                              → AI: 你好赵亮
第2轮：[用户:我叫赵亮, AI:你好赵亮, 用户:我叫什么]   → AI: 你叫赵亮 ✅
```

```tsx
const sendMessage = async () => {
  if (!input.trim()) return;

  const userMsg = { role: "user", content: input };
  const newMessages = [...messages, userMsg];  // ← 改动1：先算出包含本句话的完整历史
  setMessages(newMessages);
  setInput("");
  setLoading(true);

  const response = await fetch("http://localhost:8000/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },  // ← 改动2：告诉后端我发的是 JSON（必须有）
    body: JSON.stringify({ messages: newMessages }),   // ← 改动3：发完整历史，不再用 ?message= 参数
  });

  const reader = response.body?.getReader();
  const decoder = new TextDecoder();
  let aiContent = "";

  setMessages(prev => [...prev, { role: "assistant", content: "" }]);

  while (reader) {
    const { done, value } = await reader.read();
    if (done) break;
    aiContent += decoder.decode(value);
    setMessages(prev => {
      const newMsgs = [...prev];
      newMsgs[newMsgs.length - 1] = { role: "assistant", content: aiContent };
      return newMsgs;
    });
  }
  setLoading(false);
};
```

> 💡 三处改动，本质就一件事：从“发一句话”变成“发完整历史”。请求方式也从 URL 参数换成了 JSON body——POST 传复杂数据的标准方式，你做前端应该很熟。
>
> ⚠️ 注意：原来 URL 后面的 `?message=` 参数要**删掉**，现在数据放在 body 里。

```python
@app.post("/api/upload")
async def upload(file: UploadFile = File(...)):
    """文档上传接口"""
    # 1. 校验文件类型
    ext = os.path.splitext(file.filename)[1].lower()  # 取后缀，如 ".txt"
    if ext not in ALLOWED_EXT:
        raise HTTPException(status_code=400, detail=f"不支持的文件类型: {ext}")

    # 2. 生成随机文件名，防止同名文件互相覆盖（原名返回给前端展示用）
    save_name = f"{uuid.uuid4().hex}{ext}"
    save_path = os.path.join(UPLOAD_DIR, save_name)

    # 3. 写入磁盘（"wb" = 以二进制写入，文件上传必须用二进制）
    content = await file.read()
    with open(save_path, "wb") as f:
        f.write(content)

    return {"filename": file.filename, "saved_as": save_name, "size": len(content)}
```

> 💡 `raise HTTPException(...)` 是 FastAPI 报错的标准方式：前端会收到 400 状态码和 detail 里的错误信息。类似前端请求里 `if (res.code !== 0) throw new Error(...)` 的后端版。

### 8.1 先看问题：为什么 AI 答不了“年假几天”

现在你去问 AI“公司年假几天”，它只能瞎猜或者编一个。原因有两个：

1. **大模型的知识有截止日期**，而且是训练时学的公开知识，不可能知道你们公司的制度。
2. **它没见过你上传的文档**。第 4 步的文件只是躺在 `uploads/` 目录里，和 AI 毫无关系。

那把整篇文档发给模型行不行？小文档勉强可以，但：

- 大模型有 **Token 上限**（输入长度限制），几十页的文档直接塞不下；
- 每次提问都带全文，**又贵又慢**（按 Token 计费）；
- 资料太长时模型会“迷失”，答非所问。

行业的标准解法叫 **RAG（Retrieval-Augmented Generation，检索增强生成）**：

> 不把所有知识塞给模型，而是**提问时先检索出最相关的一小段**，只把这一小段交给模型参考。

```
上传时（入库）：
  文档 → 提取文字 → 切成小段（切片）→ 每段转成向量 → 存入向量数据库（Chroma）

提问时（检索）：
  用户提问 → 问题也转成向量 → 在向量库里找最相似的 3 段 → 拼进提示词 → 模型基于资料回答 ✅
```

类比图书馆：入库 = 把书拆成卡片放进索引柜；提问 = 按关键词抽出最相关的几张卡片，带着卡片去答题。你不需要背下整个图书馆。

### 8.2 三个核心概念（彻底搞懂再动手）

**① Embedding（嵌入）和向量**

> 文本没法直接比较“像不像”，所以先用一个**嵌入模型（Embedding 模型）**，把一段文字变成一串数字（比如 384 个浮点数），叫**向量**。神奇之处在于：**意思相近的文字，向量在数学上也相近**。“年假制度”和“带薪休假”的向量会很接近，和“今天吃什么”的向量则离得很远。  
> 类比：每段文字被标注到一个多维坐标系的某个点上，语义相近 = 坐标相近。这个“翻译器”我们不用自己写，Chroma 内置了一个，调 `collection.add()` 时自动调用。  
> **② 向量数据库和相似度检索**  
> 普通数据库按精确匹配查（`WHERE name = 'xxx'`），向量数据库按**距离**查：拿问题的向量和库里所有向量比距离，返回最近的几条（常用余弦相似度）。我们用 **Chroma**：零配置，数据存本地文件夹，跟 SQLite 一个思路。  
> 这也是为什么用户问“假期怎么休”也能命中写着“年假制度”的切片——**语义检索，不是关键词匹配**，这是 RAG 和传统搜索的本质区别。  
> **③ 为什么要切片（Chunking）**  
> 一篇长文要切成 300 字左右的小段再向量化。因为向量是“一整段话的语义浓缩”：一篇万字文档变成一个向量，语义被搅和在一起，检索精度会很差；切成小段后，每段的向量只表达那一小段的意思，检索才准。相邻切片留一点重叠（overlap），防止一句话被拦腰截断。  
> **面试加餐：RAG 和微调（Fine-tuning）的区别？**  
> 微调 = 重新训练模型把知识学进去，贵、慢、知识更新要重训；RAG = 知识存在外部库里，检索后拼进提示词，便宜、实时可更新、还能标注来源。企业知识库场景几乎都用 RAG。

```python
def extract_text(content: bytes, ext: str) -> str:
    """从文件内容（字节）提取纯文字，不依赖磁盘文件"""
    if ext == ".pdf":
        reader = PdfReader(io.BytesIO(content))  # BytesIO：把字节包装成内存中的“假文件”给 pypdf 读
        return "\n".join((page.extract_text() or "") for page in reader.pages)
    return content.decode("utf-8", errors="ignore")  # errors="ignore"：遇到编码怪异的字节直接跳过，不崩

def split_text(text: str) -> list:
    """长文切片：每片最多 CHUNK_SIZE 字，相邻两片重叠 CHUNK_OVERLAP 字"""
    text = text.replace("\n", " ")   # 换行压成空格，避免列表、标题被拆散后语义断裂
    chunks = []
    start = 0
    while start < len(text):
        end = start + CHUNK_SIZE
        chunk = text[start:end]
        if chunk.strip():            # 纯空白片段跳过（如文件末尾）
            chunks.append(chunk)
        start = end - CHUNK_OVERLAP  # 往回退 overlap 长度，保证重叠区内容不丢（见 8.2 ③）
    return chunks
```

> 💡 这两个函数对应 8.1 图里“入库”链路的前两步：提取文字、切片。第三步“转向量”不用写代码，`collection.add()` 自动完成。  
> 切片算法是“滑动窗口”：取 0~~300 字为第 1 片，然后从 250 字开始取第 2 片（250~~550），以此类推——所以相邻两片有 50 字重叠。

> 💡 这段代码的三个关键设计：
>
> 1. **`collection.upsert()` 三件套**：`documents` 存内容、`ids` 是唯一主键、`metadatas` 存额外信息（不参与检索，查询时原样带回）。类比关系型数据库：文档 = 字段值，id = 主键，metadata = 其他列。`upsert`（update + insert）和 `add` 的区别：`add` 遇到已存在的 ID 会报错，`upsert` 就地更新——所以重复上传不报错也不重复。
> 2. **内容哈希去重**：不用“哪次上传”（随机名）标识文件，改用“内容本身”（MD5 指纹）——相同内容指纹必相同，磁盘文件名和切片 id 都用指纹，重复上传自然撞上同一批 id，实现**幂等**（传多少次结果都一样）。这和前端打包产物文件名带 hash、缓存 ETag 是同一个思路：内容寻址。选 MD5 不选 SHA-256，因为目的是内容寻址而非密码学安全，MD5 更快更短。注意：去重只防“相同内容重复传”，**修改内容**后再传是新指纹，新旧版本会共存，按文件名覆盖更新是后续优化项。
> 3. **先校验后落盘（无副作用失败）**：提取、切片这类“内容能不能用”的校验放在写盘之前，不合格直接 400 拒收——磁盘不会留下垃圾文件，库里不会进脏数据，用户当场就知道原因（前端第 4 步写的错误弹窗分支自动接住）。这是文件上传类接口的最佳实践，术语叫**失败无副作用**。

@app.post("/api/chat")
async def chat(req: ChatRequest):
    """流式对话接口（支持多轮上下文 + 知识库检索）"""
    messages = req.messages

    # ===== RAG 核心 1：检索 =====
    # 用用户最新一句话去知识库里找最相关的 3 个切片（问题自动转向量、自动比距离）
    if collection.count() > 0:          # 知识库里有文档才检索，空的直接跳过，避免报错
        last_question = messages[-1]["content"]
        # include 参数：除了文档原文，把“距离”也返回回来（距离越小越相关）
        results = collection.query(
            query_texts=[last_question],
            n_results=3,
            include=["documents", "distances"]
        )
        # 相关性过滤：只保留距离 < 1.2 的切片，无关问题（如闲聊）会被全部过滤掉（阈值是经验值，可自行调）
        retrieved = [
            doc for doc, dist in zip(results["documents"][0], results["distances"][0])
            if doc and doc.strip() and dist < 1.2
        ]
    else:
        retrieved = []

    # ===== RAG 核心 2：拼提示词 =====
    # 检索到资料，就以 system 消息的身份放在对话历史最前面（模型会把它当“背景知识”）
    if retrieved:
        context = "\n\n".join(retrieved)
        system_prompt = (
            "你是企业知识库助手。以下是参考资料：\n\n"
            f"{context}\n\n"
            "请基于以上参考资料回答用户问题。"
            "如果资料中没有相关内容，请如实说‘知识库中未提及’，不要编造。"
        )
        messages = [{"role": "system", "content": system_prompt}] + messages

    def generate():
        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=messages,   # 注意：用的是拼好资料的 messages，不是 req.messages
            stream=True
        )
        for chunk in response:
            if chunk.choices[0].delta.content:
                yield chunk.choices[0].delta.content

    return StreamingResponse(generate(), media_type="text/plain")
```

> 💡 三个新知识点：
>
> 1. **`system` 角色**：第 3 步说过 role 有 user / assistant / system 三种。system 消息不对用户展示，用来给模型“立规矩、垫背景”。RAG 检索到的资料就是垫在这里。
> 2. **“不要编造”这句提示词不是废话**：大模型天生爱“一本正经地胡说”（术语叫**幻觉**），明确要求它基于资料回答、不知道就说不知道，是 RAG 工程的标配。
> 3. **距离阈值过滤**：向量检索永远会返回“最接近的 N 条”，哪怕毫不相关——不过滤的话闲聊也会被注入知识库人设。让 `query` 连距离一起返回，距离超阈值的丢弃，这是生产环境控制检索相关性的标准做法，面试必问。

**问：什么是 RAG？解决什么问题？**

> RAG = 检索增强生成。大模型有知识截止、不了解私有数据、容易幻觉三个问题；RAG 在提问时先从知识库检索相关内容，拼进提示词让模型基于资料回答，知识可实时更新、可追溯来源，是企业知识库的标准方案。

> 用嵌入模型把文本映射成高维向量，语义相近的文本向量距离近。提问和文档都转向量后，用余弦相似度找最近邻，就实现了语义检索（区别于关键词匹配）。

> 可以设相似度阈值，距离太远就不采用；同时在提示词里要求模型“资料没有就说不知道”，双保险压幻觉。这也是第 6 步引用溯源的基础：回答标注来自哪份文档，用户可自行验证。

### 9.1 为什么必须做引用溯源（先想明白价值）

没有溯源的知识库有三个硬伤：

1. **不可验证**：用户不知道答案是来自文档还是模型编的，不敢信；
2. **出错无法定位**：答错了不知道是哪份文档、哪个切片的问题，没法修；
3. **责任不清**：企业场景里“AI 说的”不能作为依据，“出自《员工手册》第几条”才可以。

做完这步，压幻觉的手段集齐三件套：**提示词约束**（第 5 步）+ **阈值过滤**（第 5 步）+ **来源可验证**（本步）——面试讲幻觉治理时按这个顺序说。

### 9.2 三个核心概念（本步的知识主线）

**① SSE（Server-Sent Events）：带类型的流**

现在的 `/api/chat` 返回的是裸文字流（`text/plain`），只有一种内容。但“引用来源”是结构化数据（JSON），不能混进文字流——你没法分辨收到的 `[{...}]` 是来源还是回答的一部分。

SSE 在流之上加了消息结构：

```
event: sources
data: [{"id":1,"filename":"公司制度.txt","snippet":"..."}]

event: token
data: {"content":"入"}

event: token
data: {"content":"职"}

event: done
data: {}
```

规则：每条消息由 `event:`（类型）和 `data:`（内容）组成，**空行是消息边界**。Content-Type 是 `text/event-stream`。前端按类型分发：`sources` 渲染引用卡片，`token` 追加文字，`done` 结束。

> 💡 为什么 `data` 里包 JSON 而不是裸文字？因为回答的 token 可能含换行符，而 SSE 里换行有特殊含义（分隔 data 行）——裸文字会撕裂消息帧。`json.dumps` 会把 `\n` 转义成 `\\n`，天然安全。DeepSeek/OpenAI 的官方流式接口也是这个格式（`data: {...}`，最后 `data: [DONE]`）。

**② metadata 兑现：每个切片自带的“出身证明”**

第 5 步入库时存了 `metadatas=[{"filename": ...}]`，当时说“第 6 步要用”。现在检索时把 `include` 加个 `"metadatas"`，每个切片就会带回自己的文件名——溯源的原料早准备好了。

**③ 编号引用：提示词 + 来源列表的配合**

拼提示词时给每段资料编号：`[1] (来自: 公司制度.txt) 内容...`，并要求模型“引用时在句尾标 [1]”。同时把同样的编号列表发给前端渲染卡片——**模型标的号和前端卡片的号必须是同一套编号**，这是全链路设计的核心：后端一处编号，提示词和前端都消费它。

### 9.3 依赖：零新增（本步不装任何包）

`json` 是 Python 标准库，SSE 就是普通 HTTP 响应——本步是纯代码改造，体会一下“协议升级不等于弓新依赖”。

        hits = [
            (doc, meta) for doc, dist, meta in zip(
                results["documents"][0], results["distances"][0], results["metadatas"][0])
            if doc and doc.strip() and dist < 1.2
        ]
    else:
        hits = []

    # ===== 新增：构建编号引用源（按“文件名+内容”去重，重复切片只算一条来源）=====
    sources = []          # 发给前端的卡片列表：[{id, filename, snippet}]
    context_parts = []    # 拼进提示词的编号资料：[1] (来自: xx) 内容...
    seen = set()
    for doc, meta in hits:
        key = (meta.get("filename"), doc)
        if key in seen:
            continue
        seen.add(key)
        sources.append({"id": len(sources) + 1, "filename": meta.get("filename", "未知来源"), "snippet": doc})
        context_parts.append(f"[{len(sources)}] (来自: {meta.get('filename', '未知来源')})\n{doc}")

    # ===== RAG 核心 2：拼提示词（升级为“编号版”，并要求模型标注引用）=====
    if sources:
        context = "\n\n".join(context_parts)
        system_prompt = (
            "你是企业知识库助手。以下是参考资料，每条以编号开头：\n\n"
            f"{context}\n\n"
            "请基于以上参考资料回答用户问题。要求：\n"
            "1. 在引用了资料的句子末尾标注资料编号，如 [1]，编号只能来自上述资料；\n"
            "2. 如果资料中没有相关内容，请如实说‘知识库中未提及’，不要编造。"
        )
        messages = [{"role": "system", "content": system_prompt}] + messages

    def generate():
        # ① 先发 sources 事件：结构化数据单独一条消息，先于正文到达，前端可提前渲染卡片
        if sources:
            yield f"event: sources\ndata: {json.dumps(sources, ensure_ascii=False)}\n\n"

        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=messages,
            stream=True
        )
        # ② 逐字流式：每个 token 包成一条 token 事件（JSON 转义保证换行不撕裂消息帧）
        for chunk in response:
            if chunk.choices[0].delta.content:
                piece = chunk.choices[0].delta.content
                yield f"event: token\ndata: {json.dumps({'content': piece}, ensure_ascii=False)}\n\n"

        # ③ 结束事件：明确告诉前端流结束了（不依赖连接断开来判断）
        yield "event: done\ndata: {}\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream")   # ← text/plain 换掉了
```

> 💡 这段代码的三个关键设计：
>
> 1. **一处编号，三处消费**：`sources` 列表的 id 同时出现在——提示词的资料编号、模型回答里的 [n]、前端卡片——三者能对齐全靠后端这一处统一编号。
> 2. **`ensure_ascii=False`**：默认会把中文转成 `\u516c\u53f8` 这种转义，功能不受影响但 DevTools 里没法直接读；关掉后 `data` 里就是可读中文，调试体验天壤之别。
> 3. **done 事件的意义**：前端不应该靠“连接断了”猜结束——网络抖动也会断。显式的结束事件是流式协议的标配设计（OpenAI 的 `data: [DONE]` 同理）。
>
> ⚠️ 替换后先别急着测前端，先用 curl 验后端（见 9.6 场景 1），确认流的格式对了再动前端。

### 9.5 改前端：`frontend/src/app/page.tsx`（三处）

**① 消息类型加 `sources` 字段**（文件开头附近）：

把 `const [messages, setMessages] = useState<{role: string, content: string}[]>([]);` 换成：

```tsx
type Source = { id: number; filename: string; snippet: string };
type Msg = { role: string; content: string; sources?: Source[] };

// 组件内：
const [messages, setMessages] = useState<Msg[]>([]);
```

**② 升级 `sendMessage` 的流式解析段**：把从 `const reader = response.body?.getReader();` 到 `setLoading(false);` 之间（含这两行）替换成：

```tsx
    const reader = response.body?.getReader();
    const decoder = new TextDecoder();
    let aiContent = "";
    let buffer = "";   // SSE 缓冲区：网络分包和消息边界不对齐，必须攒够一条完整消息再解析

    setMessages(prev => [...prev, { role: "assistant", content: "" }]);

    while (reader) {
      const { done, value } = await reader.read();
      if (done) break;
      buffer += decoder.decode(value, { stream: true });   // stream:true 防中文被拦腰截成乱码（多字节字符）

      // 一条完整的 SSE 消息以空行 "\n\n" 结束；最后一段可能不完整，留在 buffer 里等下一轮
      const events = buffer.split("\n\n");
      buffer = events.pop() ?? "";

      for (const evt of events) {
        if (!evt.trim()) continue;
        let name = "";
        let data = "";
        for (const line of evt.split("\n")) {
          if (line.startsWith("event:")) name = line.slice(6).trim();
          else if (line.startsWith("data:")) data = line.slice(5).trim();
        }
        if (!data) continue;
        const payload = JSON.parse(data);

        if (name === "sources") {
          // 来源事件：写进当前 AI 消息的 sources 字段（卡片会立刻渲染出来，不用等回答完成）
          setMessages(prev => {
            const next = [...prev];
            next[next.length - 1] = { ...next[next.length - 1], sources: payload };
            return next;
          });
        } else if (name === "token") {
          aiContent += payload.content;
          setMessages(prev => {
            const next = [...prev];
            next[next.length - 1] = { ...next[next.length - 1], content: aiContent };
            return next;
          });
        }
        // done 事件：无需处理，流结束后下面会重置 loading
      }
    }
    setLoading(false);
```

> 💡 这段里藏着一个前端流式开发的经典坑：**buffer 机制**。`reader.read()` 返回的网络块和 SSE 消息边界完全不对齐——一条消息可能被勈成两个块，一个块里也可能有三条消息。所以必须攒进 buffer、按 `\n\n` 切、把不完整的尾巴留着。你以前用 WebSocket 没遇到过这个问题，因为 WebSocket 天然按消息分帧；HTTP 流没有这个待遇，要自己拼。
>
> 另一个坑：`decoder.decode(value, { stream: true })` 的 `stream: true` 不能省。中文在 UTF-8 里占 3 个字节，网络块可能从中间截断，不加这个参数会把半个汉字解码成乱码 `\uFFFD`。

**③ 渲染引用卡片**：把消息列表的 `{msg.content}` 所在的那个气泡容器后面（`</div>` 闭合后、外层 `<div key={i}>` 闭合前）加一段：

```tsx
            {msg.sources && msg.sources.length > 0 && (
              <div className="mt-2 text-xs text-gray-500 space-y-1 max-w-md">
                {msg.sources.map(s => (
                  <details key={s.id} className="bg-gray-50 border rounded px-2 py-1">
                    <summary className="cursor-pointer select-none">
                      [{s.id}] {s.filename}
                    </summary>
                    <div className="mt-1 whitespace-pre-wrap leading-relaxed">{s.snippet}</div>
                  </details>
                ))}
              </div>
            )}
```

> 💡 `<details>/<summary>` 是浏览器原生的折叠组件，零 JS、零状态——点击展开/收起完全由浏览器接管。这种“能用原生标签就不写状态”的习惯，面试官看到会加分。
>
> 注意消息渲染处的类型：现在 `messages.map((msg, i) => ...)` 里的 `msg` 自动获得 `Msg` 类型（因为 useState 的泛型换了），直接用 `msg.sources` 不会报错。
>
> 回答正文里的 `[1]` 标记会原样显示在气泡里——暂不做高亮渲染，先把链路跑通，“把 [n] 渲染成可点击的样式”列为后续优化项。

### 9.7 常见坑（本步的坑集中在“流的解析”上）

| 现象                  | 原因与解决                                                   |
| ------------------- | ------------------------------------------------------- |
| 前端报 `JSON.parse` 错误 | 没做 buffer，半条消息就解析了。对照 9.5 ② 的 buffer 机制逐行检查             |
| 中文乱码 `\uFFFD`       | `decoder.decode` 没加 `{ stream: true }`                  |
| 回答里的 [3] 没有对应卡片     | 模型编造了不存在的编号（提示词没压住）。属模型行为，前端可忽略越界编号；优化项：后端校验后再转发        |
| 卡片里文件名是“未知来源”       | 入库时没存 metadata（比如清空过知识库后的旧切片）。重传一次文档即可                  |
| Swagger 里测 chat 很别扭 | event-stream 在 Swagger 里展示不友好，用 curl 或前端测               |
| sources 事件没到前端      | 检查知识库是否为空、阈值是否全滤掉了（后端终端加一行 `print(sources)` 看）          |
| 部署后流式失效（以后会遇到）      | Nginx 默认缓冲响应，需加 `proxy_buffering off`——部署步骤（第 10 步）时的伏笔 |
| 卡片展开后换行丢了一半         | 忘了 `whitespace-pre-wrap`，原文里的换行会被 HTML 折叠               |

### 9.8 面试知识点（本步能把“玩具项目”和“产品”区分开）

**问：RAG 怎么做引用溯源？**

> 入库时把来源信息（文件名）存进切片的 metadata；检索时连 metadata 一起取回；拼提示词时给每段资料编号，并要求模型引用时标注编号；同时把编号来源列表通过 SSE 单独事件发给前端渲染。后端一处编号、提示词和前端两处消费，三者对齐。还能加一层校验：模型引用了不存在的编号就剔除。

**问：为什么用 SSE？和 WebSocket 什么区别？**

> LLM 流式回答是单向的（服务端→客户端），SSE 基于普通 HTTP、天然支持重连和代理穿透，够用且更简单；WebSocket 是全双工，适合聊天室这类双向场景。流式输出选 SSE 是行业惯例（OpenAI/DeepSeek 都是）。
>
> **追问：那为什么前端不用浏览器原生的 EventSource？**  
> 因为 EventSource 只支持 GET 请求，而我们的对话要 POST 带历史消息，所以用 fetch 手动解析 SSE 流——这也是为什么主流 AI 产品的前端都是自己写解析器。

**问：模型乱标引用编号怎么办？**

> 三道防线：提示词明确约束“编号只能来自上述资料”；降低单次引用的资料条数（资料越少越不容易标错）；前端/后端做越界校验，忽略或剔除不存在的编号。本质是模型的概率性行为，只能约束不能根除，工程上要有兑底。
>
> **问：同一份文档多个切片命中，来源列表怎么处理？**  
> 按“文件名+内容”去重后编号；更产品化的做法是按文件聚合，一个文件一张卡片，里面列出多个命中片段。
>
> **问：为什么 data 里包 JSON？**  
> 因为 token 可能含换行符，而 SSE 里换行是消息帧的分隔符，裸文字会撕裂消息；JSON 转义天然规避，还能携带结构化字段。
>
> **问：前端解析流为什么要 buffer？**  
> HTTP 流的网络分包和消息边界不对齐（一个块里可能有多条消息，一条消息也可能被勈在两个块里），必须按 `\n\n` 切完整消息、不完整的尾巴攒到下一轮。WebSocket 没这个问题是因为它天然按消息分帧。
